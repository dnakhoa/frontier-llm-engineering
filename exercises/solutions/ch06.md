## 6.1 🔢 The memory wall

**1. Bytes per parameter.**

| Tensor | Precision | Bytes |
|---|---|---|
| BF16 working weights | BF16 | 2 |
| BF16 gradients | BF16 | 2 |
| FP32 master weights | FP32 | 4 |
| Adam $m$ | FP32 | 4 |
| Adam $v$ | FP32 | 4 |
| **Total** | | **16** |

**2. 70B total.** $70\times10^9 \times 16 = \mathbf{1{,}120 \text{ GB}}$.

**3. H100s required.** $1{,}120 / 80 = \mathbf{14 \text{ GPUs}}$ — for parameters alone, with zero activations, zero communication buffers, and zero CUDA context.

**4. Larger models.**

| Model | Parameters | Static memory | H100s (static only) |
|---|---|---|---|
| 70B | $7\times10^{10}$ | 1,120 GB | 14 |
| 405B | $4.05\times10^{11}$ | 6,480 GB | 81 |
| DeepSeek-V3 | $6.71\times10^{11}$ | 10,736 GB | **134** |

**5. Why total, not active, for MoE.**

Because **every parameter needs its own optimizer state and gradient slot, whether or not it was selected this token.** Adam's $m$ and $v$ are per-parameter and persist across steps; a parameter that was inactive for the last thousand steps still has an $m$ and a $v$ occupying 8 bytes.

Active parameters determine **compute** ($6ND$ uses active). Total parameters determine **memory**. This is §5.3's MoE bargain restated, and it is the single most common confusion about MoE — people reason about a 671B MoE as though it were a 37B model, and it is a 37B model *for FLOPs* and a 671B model *for memory*.

## 6.2 🔢 ZeRO stages

70B model, 64 data-parallel ranks. Per-parameter: 2 (BF16 weights) + 2 (grads) + 12 (FP32 master + $m$ + $v$).

**1. Plain DDP.** Nothing sharded: $70\times10^9 \times 16 = \mathbf{1{,}120 \text{ GB per GPU}}$. Does not fit anything.

**2. ZeRO-1** — optimizer state (12 bytes) sharded:

$$70\times10^9 \times \left(2 + 2 + \frac{12}{64}\right) = 70\times10^9 \times 4.1875 = \mathbf{293 \text{ GB}}$$

**3. ZeRO-2** — optimizer state and gradients sharded:

$$70\times10^9 \times \left(2 + \frac{2}{64} + \frac{12}{64}\right) = 70\times10^9 \times 2.21875 = \mathbf{155 \text{ GB}}$$

**4. ZeRO-3 / FSDP** — everything sharded:

$$\frac{70\times10^9 \times 16}{64} = \mathbf{17.5 \text{ GB}}$$

**5. First stage that fits in 80 GB.** **ZeRO-3.** ZeRO-2 at 155 GB is still nearly double an H100.

This is the arithmetic that made FSDP the default for large dense models: nothing below full sharding fits a 70B model on a 64-GPU cluster.

**6. What ZeRO-3 costs, and when it is free.**

Parameters are sharded, so before computing layer $\ell$ every rank must **all-gather** that layer's full parameters, use them, and discard them. Per step, the all-gather volume is the full parameter set (2 bytes/param in BF16) — once for the forward and typically again for the backward — plus a **reduce-scatter** of gradients.

**When it is free:** when it is *overlapped with computation*. FSDP prefetches layer $\ell+1$'s parameters while layer $\ell$ is still computing. If the all-gather for one layer completes faster than the compute for the previous layer, the communication is entirely hidden.

$$\text{free if} \quad \frac{\text{bytes per layer}}{\text{bandwidth}} < \frac{\text{FLOPs per layer}}{\text{compute rate}}$$

This holds comfortably within a node over NVLink, and it is exactly why FSDP degrades badly when the data-parallel group spans slow interconnect: the prefetch can no longer keep ahead of the compute, and the GPUs stall waiting for parameters. It is the same overlap-or-stall question that recurs in §6.11 and §20.11.

## 6.3 🔢 Activation memory

**1. One layer.** The tensors a pre-norm transformer layer must retain for the backward pass, per token, in units of $d$:

| Tensor | Multiples of $d$ |
|---|---|
| Layer input (residual) | 1 |
| Post-attention-norm output | 1 |
| Q, K, V | 3 (at GQA 8:1, closer to 1 + 0.125 + 0.125) |
| Attention output pre-projection | 1 |
| Post-FFN-norm output | 1 |
| FFN gate and up projections | $2 \times (d_{\text{ff}}/d) = 7$ |
| FFN activation product | $d_{\text{ff}}/d = 3.5$ |

Roughly **15–20 multiples of $d$ per token**. Take 16 as a working figure.

$$16 \times 8192 \times 8192 \text{ tokens} \times 2 \text{ bytes} = \mathbf{2.15 \text{ GB per layer}}$$

**2. All 80 layers.** $\mathbf{172 \text{ GB}}$ — at micro-batch size **1**.

**3. Which dominates?**

Static (from §6.2, ZeRO-3 on 64 ranks): 17.5 GB. Activations: 172 GB.

**Activations dominate by roughly 10×**, and this is the result that surprises people. Every discussion of "will the model fit" focuses on parameters, and at realistic sequence lengths the activations are the larger term.

Note also what activations do *not* do: they do not shard across data-parallel ranks. Each rank holds the activations for its own micro-batch. ZeRO helps the 17.5 GB and does nothing for the 172 GB.

**4. Full recomputation.**

Store only each layer's **input** — 1 multiple of $d$ instead of 16:

$$\frac{172}{16} \approx \mathbf{11 \text{ GB}}$$

The cost: the entire forward pass is recomputed during the backward, so total compute goes from (1 forward + 2 backward) to (2 forward + 2 backward) — **roughly +33%**.

**5. Selective recomputation.**

Korthikanti et al. observe that the tensors are not equal: some are **large and cheap to recompute** (the attention softmax and dropout masks, which are $O(s^2)$ in memory but trivially recomputed), and others are **small and expensive** (the outputs of the big GEMMs).

Selective recomputation **stores the GEMM outputs and recomputes the attention internals.** You keep the tensors whose recomputation cost is high relative to their size, and drop the ones whose recomputation is nearly free.

Result: most of the memory saving for roughly a third of the compute overhead — about +10% instead of +33%. It is the default in Megatron for this reason, and it is a good example of a general principle: **when trading memory for compute, do it per-tensor rather than uniformly.**

## 6.4 🔢 Communication volume

**1. Bytes all-reduced per step under DDP.**

Gradients, BF16, all parameters:

$$70\times10^9 \times 2 = \mathbf{140 \text{ GB}}$$

Independent of batch size — this is the point that catches people. Gradient communication scales with *parameters*, not with tokens.

**2. Ring all-reduce per-rank traffic.**

$$140 \text{ GB} \times \frac{2(N-1)}{N} = 140 \times \frac{2 \times 63}{64} = \mathbf{275.6 \text{ GB}}$$

(Approaching $2\times$ the payload as $N$ grows.)

**3. Time at 400 Gb/s.**

$400 \text{ Gb/s} = 50 \text{ GB/s}$. Assume ~80% achieved, so 40 GB/s:

$$\frac{275.6}{40} = \mathbf{6.9 \text{ seconds}}$$

**4. Fraction of an 8-second step.**

$$\frac{6.9}{8} = \mathbf{86\%}$$

**Not remotely acceptable.** If communication is not overlapped, this configuration spends more time talking than computing.

Three things make it survivable in practice, and every real system uses all three:

- **Overlap.** Gradients for layer $\ell$ are ready as soon as layer $\ell$'s backward completes, so their all-reduce can start while layer $\ell-1$ is still computing. Done properly, most of the 6.9 s hides behind the 8 s.
- **Bucketing.** Fusing many small gradient tensors into large contiguous buffers, because 80% of link bandwidth is only achievable on large messages.
- **Gradient accumulation.** Communicating once per *optimizer* step rather than once per micro-batch. With 8 accumulation steps, the same 275 GB is amortized over 8× the compute.

**5. ZeRO-3 communication.**

The all-reduce is replaced by:

- **All-gather of parameters** in the forward: $70\times10^9 \times 2 = 140$ GB
- **All-gather again** in the backward: 140 GB (or store from the forward, trading memory)
- **Reduce-scatter of gradients**: 140 GB

Total ~**420 GB**, roughly **1.5× the DDP all-reduce volume** in payload terms — though the per-rank ring traffic works out closer to comparable, since all-gather and reduce-scatter each move $(N-1)/N$ rather than $2(N-1)/N$.

The honest summary: **ZeRO-3 trades roughly 1.5× the communication for an 64× reduction in static memory.** Whether that is a good trade depends entirely on whether the communication overlaps (§6.2 part 6), which depends on your interconnect.

## 6.5 🔢 The pipeline bubble

**1. Derivation.**

With $P$ stages and $M$ micro-batches, the pipeline takes $P - 1$ steps to fill and $P - 1$ to drain. Total time in units of one micro-batch stage-time: $M + P - 1$. Useful time: $M$.

$$\text{bubble fraction} = \frac{(M + P - 1) - M}{M + P - 1} = \frac{P - 1}{M + P - 1}$$

**2. Values.**

| $P$ | $M$ | Bubble |
|---|---|---|
| 8 | 8 | $7/15 = \mathbf{46.7\%}$ |
| 8 | 32 | $7/39 = \mathbf{17.9\%}$ |
| 16 | 32 | $15/47 = \mathbf{31.9\%}$ |

Nearly half the machine idle at $M = P$. This is why naive pipeline parallelism has a bad reputation.

**3. Rule of thumb.** $M \gtrsim 4P$, which puts the bubble under ~20%. $M \gtrsim 8P$ gets under 11%.

**4. Interleaved 1F1B.**

Each device holds $v$ non-contiguous chunks of layers rather than one contiguous block, so the pipeline has $vP$ virtual stages but the same $P$ devices. The bubble becomes $\frac{P-1}{v M + P - 1}$ — divided by roughly $v$.

**The cost:** $v\times$ more pipeline communication, because activations cross device boundaries $v$ times per micro-batch instead of once. You are trading bandwidth for bubble, which is a good trade when the pipeline links are fast and a bad one when they are not.

**5. Why not just make $M$ huge?**

Three limits, and the first is the binding one:

- **Activation memory.** With 1F1B, a stage holds activations for up to $P$ in-flight micro-batches. Increasing $M$ does not increase this (that is 1F1B's whole point over GPipe), but increasing $M$ at a *fixed global batch* means shrinking the micro-batch, and…
- **Micro-batch efficiency.** Below a certain micro-batch size, the per-layer GEMMs are too small for good tensor-core utilization. You have traded a pipeline bubble for a compute-efficiency loss.
- **Global batch size is a hyperparameter, not free.** $M \times \text{micro-batch} \times \text{DP}$ = global batch, and the global batch is constrained by the critical-batch-size argument in §8.14. You cannot inflate it without changing the optimization.

## 6.6 🔢 Expert parallelism and the all-to-all

**1. Token-copies dispatched per layer.**

$$4{,}096 \text{ tokens} \times 8 \text{ (top-}k\text{)} = \mathbf{32{,}768 \text{ token-copies}}$$

**2. Dispatch bytes per GPU.**

Each token-copy is a $d$-dimensional activation:

$$32{,}768 \times 7{,}168 \times 2 \text{ bytes} = \mathbf{470 \text{ MB}}$$

With 8-way EP, roughly $7/8$ of that leaves the GPU: **411 MB**.

**3. Plus combine.** The results come back the same way: **~940 MB per layer** (dispatch + combine), of which ~822 MB crosses the network.

**4. Over 60 layers.**

$$60 \times 0.94 \text{ GB} \approx \mathbf{56 \text{ GB per micro-batch, per GPU}}$$

**5. Versus the DP all-reduce, and where to place EP ranks.**

The DP all-reduce (§6.4) was ~276 GB per rank **per optimizer step**. The all-to-all is ~56 GB per rank **per micro-batch** — and with, say, 16 micro-batches accumulated per step, that is **~900 GB per step**.

**The all-to-all dominates by roughly 3×**, and it has a worse profile: it happens twice per layer, it is on the critical path (you cannot compute the expert output before the tokens arrive), and it is a scatter rather than a ring, so it achieves lower bandwidth utilization.

**Implication for placement: expert-parallel ranks must be on the fastest interconnect available**, which means within a node over NVLink wherever possible. Data-parallel ranks, whose communication is a once-per-step overlappable all-reduce, are the ones you spread across the slow inter-node network.

This is the central topology-aware placement decision for MoE training (§7.4), and it is the reason DualPipe exists: even on NVLink, hiding a 900 GB/step all-to-all behind computation requires deliberate scheduling.

## 6.7 🏗️ Size a run

**1. Questions to ask first** — this part is scored, and answering immediately scores badly.

- What is the target wall-clock, and is there a hard deadline?
- Is the 8T tokens fixed, or is it the compute budget that is fixed?
- What context length at the *end* of training — is there a long-context extension phase (§9.3)?
- What precision? Is FP8 available and validated, or BF16?
- What is the expert count and top-$k$? (Given only "200B/25B," the sparsity structure is unspecified and it determines EP.)
- Is the interconnect topology fat-tree or rail-optimized? Any oversubscription?
- What is the checkpoint storage bandwidth?
- Is this the first run of this recipe, or a scale-up of something validated?

The last one matters most in practice: a first run should be configured conservatively for debuggability, not for peak MFU.

**2. Parallelism, with the arithmetic.**

Assume 128 experts, top-8, in the absence of a stated structure.

Static memory, 200B total at 16 bytes/param: **3,200 GB**. Across 1,024 GPUs of 80 GB = 81,920 GB total, so 3.9% — comfortable in aggregate, and §1.3 part 4's warning applies.

Proposed: **TP = 1, PP = 4, EP = 8, DP = 32.** ($1 \times 4 \times 8 \times 32 = 1{,}024$.)

- **TP = 1.** Following DeepSeek-V3's approach (§6.9): with MoE, the FFN parallelism is already provided by EP, and skipping TP eliminates two all-reduces per layer. Requires that a single expert's weights fit on one GPU, which at $d_{\text{ff}}$ per expert of a few thousand they comfortably do.
- **EP = 8.** Within a node, over NVLink — this is the §6.6 conclusion, and it is the most important placement decision here. 128 experts / 8 = 16 experts per GPU.
- **PP = 4.** Across nodes. Pipeline sends only layer-boundary activations, which is the cheapest inter-node traffic available.
- **DP = 32.** The remainder, with ZeRO-1 sharding the optimizer state across it.

Per-GPU memory:
- Parameters (sharded by EP × PP): $200\times10^9 \times 2 / 32 = 12.5$ GB
- Gradients: 12.5 GB
- Optimizer state, ZeRO-1 over DP=32: $200\times10^9 \times 12 / (32 \times 32) = 2.3$ GB
- Subtotal: **~27 GB**, leaving ~50 GB for activations and buffers.

**3. Batch.**

Micro-batch 1, sequence 8,192. With PP = 4, want $M \gtrsim 16$ (§6.5) → bubble $3/19 = 16\%$. Take $M = 16$ gradient-accumulation steps.

Global batch $= 1 \times 8{,}192 \times 16 \times 32 = \mathbf{4.19\text{M tokens}}$ — a reasonable figure for this scale (§8.14).

**4. Recomputation.** **Selective** (§6.3 part 5). With ~50 GB of headroom and ~172 GB of naive activation demand scaled down by PP=4 to ~43 GB, we are near the edge — selective recomputation brings it well inside with ~10% compute overhead. Full recomputation would be leaving throughput on the table.

**5. MFU and wall clock.**

$$\text{FLOPs} = 6 \times 25\times10^9 \times 8\times10^{12} = 1.2\times10^{24}$$

At 990 TFLOP/s BF16 × 1,024 GPUs × assumed 35% MFU (MoE runs lower than dense, because of the all-to-all and expert-size inefficiency):

$$\frac{1.2\times10^{24}}{1.014\times10^{18} \times 0.35} = 3.38\times10^6 \text{ s} = \mathbf{39 \text{ days}}$$

**6. Three things most likely to make this wrong.**

- **The all-to-all does not overlap as well as assumed**, and MFU comes in at 20% rather than 35%. This is the single largest risk and it turns 39 days into 68.
- **Expert load imbalance** (§5.7) — a synchronous collective means the slowest GPU sets the pace, and a persistent 1.5× imbalance is a 50% throughput loss.
- **Failures and restarts.** At 1,024 GPUs, a failure every ~2 days (Ex 1.8), so ~20 interruptions over the run. If each costs an hour rather than 20 minutes, that is a lost day.

**7. With 100 Gb/s Ethernet instead of InfiniBand.**

This changes the answer substantially, and recognizing that is the point of part 7.

- Inter-node bandwidth drops 4×, and Ethernet without RoCE has worse latency and worse collective performance than the raw number suggests.
- **EP must stay strictly intra-node.** It already was, which is fortunate — if it were not, this configuration would be unusable.
- **DP=32 over Ethernet is the problem.** The §6.4 all-reduce at 4× less bandwidth means ~27 s of communication against ~8 s of compute. Even with perfect overlap it cannot hide.
- **Mitigations:** increase gradient accumulation substantially (more compute per communication), consider hierarchical all-reduce (reduce within node over NVLink, then across nodes), and switch from ZeRO-1 to plain DDP with the optimizer replicated, accepting the memory cost to avoid ZeRO's extra collectives.
- **Realistic outcome:** MFU drops to perhaps 20%, and the run takes ~68 days instead of 39.

The general lesson: **the interconnect determines the parallelism strategy more than the model does.** Two identical models on two clusters with different networks get genuinely different configurations.

## 6.8 🏗️ Why these degrees and not others

**1. "Keep TP within a node."**

*Mechanism:* TP does an all-reduce **twice per layer** — after attention and after the FFN — and these are on the critical path with nothing to overlap with. At 80 layers that is 160 blocking collectives per forward pass. NVLink at ~900 GB/s makes them tolerable; InfiniBand at 50 GB/s does not.

*When it is wrong:* when the model genuinely cannot fit otherwise and you have no alternative — a very large dense model where even ZeRO-3 leaves a single layer too big for one GPU. Also less wrong on clusters with fast, low-latency inter-node fabric where a 2-node TP group is survivable.

**2. "Use PP only when the model does not fit with TP and ZeRO."**

*Mechanism:* PP introduces the bubble (§6.5) and considerable scheduling complexity, and it constrains your micro-batch structure. Its virtue is that it is the *cheapest on communication* — only layer-boundary activations cross stages.

*When it is wrong:* when your interconnect is slow. On Ethernet, PP's cheap communication is exactly what you want across the slow links, and you should reach for it earlier than the rule suggests. §6.7 part 7 is this case.

**3. "Make DP as large as possible."**

*Mechanism:* DP is the most efficient axis — its communication is a once-per-step all-reduce that overlaps well (§6.4).

*When it is wrong:* when it pushes the global batch past the critical batch size (§8.14). Beyond that point, larger batches stop improving convergence per token, so you are consuming more tokens per step for no gain. You can compensate by shrinking the micro-batch, but only until GEMM efficiency suffers. This is a real ceiling and it is why very large clusters need PP and TP rather than just more DP.

**4. "EP degree should divide the expert count evenly."**

*Mechanism:* uneven division means some GPUs hold more experts than others, and since the all-to-all is synchronous, the GPU with more experts sets the pace for everyone (§5.7).

*When it is wrong:* rarely, on this axis. But note the subtler version — even division of *experts* does not give even division of *tokens*, which is the load-balance problem. Even division is necessary and not sufficient.

**5. "Micro-batch size 1 with lots of accumulation."**

*Mechanism:* micro-batch 1 minimizes activation memory (§6.3 scales linearly in it), and accumulation recovers the global batch.

*When it is wrong:* when it makes the GEMMs too small. At micro-batch 1 and sequence 8,192, the effective GEMM batch dimension is 8,192 — comfortably large. At micro-batch 1 and sequence 512, it is 512, which is small enough that tensor-core utilization suffers. The rule assumes long sequences, and it inverts for short-sequence training.

## 6.9 📄 Read the DeepSeek-V3 parallelism

**1. Degrees.** The report describes 16-way pipeline parallelism, 64-way expert parallelism spanning 8 nodes, and ZeRO-1 data parallelism, on 2,048 H800s.

**2. Why no tensor parallelism is possible, and what it buys.**

Possible because: in an MoE, the FFN — which is 80%+ of the parameters (§5.1) — is already split across devices by *expert* parallelism. TP exists primarily to split the FFN and attention matrices when they are too large for one device; with fine-grained experts ($d_{\text{ff}} = 2048$ each), no individual matrix is close to too large. MLA also keeps the attention projections modest.

What it buys: **eliminating two all-reduces per layer, on the critical path, for 60 layers.** That is 120 blocking collectives per forward pass removed. On H800s — which have reduced NVLink bandwidth relative to H100s due to export restrictions — this is not a marginal optimization; it is a large part of what made the run efficient on that hardware.

**3. DualPipe.** It overlaps the **all-to-all communication of the MoE dispatch/combine** with the **computation of a different micro-batch's forward or backward pass**, using a bidirectional pipeline schedule.

Why it matters more for MoE: a dense model's pipeline has only the layer-boundary activation transfers to hide, which are small. An MoE has the §6.6 all-to-all — ~900 GB per step per rank — sitting on the critical path of every layer. Without overlap, that is the dominant cost. DualPipe exists because MoE made pipeline scheduling a communication-hiding problem rather than a bubble-minimization problem.

**4. The all-to-all and the hardware constraint.**

They describe custom cross-node all-to-all kernels that carefully budget how many SMs are dedicated to communication versus computation, and that limit each token to being dispatched to a bounded number of *nodes* (rather than an unbounded number of experts anywhere).

**The hardware constraint that shaped it:** the H800's reduced inter-GPU bandwidth. The node-limited routing is a direct architectural accommodation to the interconnect — the routing algorithm was constrained so the communication pattern would fit the network they had.

This is the most instructive thing in the section: **the export-control-driven hardware constraint propagated all the way up into the model's routing algorithm.** Architecture and infrastructure are not separable at this scale, which is §6.8 part 1's lesson at the largest possible scope.

## 6.10 🧪 Break the memory model

**1. 70B on 8 GPUs.**

*Prediction:* ZeRO-3 will be needed.

*What you find:* ZeRO-3 alone gives $1{,}120/8 = 140$ GB per GPU — **still over 80 GB.** You need ZeRO-3 *plus* either TP=2 or offloading. This surprises people who have internalized "FSDP solves memory": with only 8 ranks, sharding by 8 is not enough for a 70B model.

The general lesson: ZeRO's benefit scales with the DP degree, so it is weakest exactly where you have few GPUs — which is where you need it most.

**2. 8K → 32K sequence length.**

*Prediction:* activation memory grows 4×.

*What happens:* the **stored-activation** term grows exactly 4× (linear in sequence length). But if attention is *not* using FlashAttention, the $O(s^2)$ attention matrix term grows **16×** and comes to dominate everything.

This is the concrete reason FlashAttention (§20.5) is what made long context possible: it is not a speed optimization here, it is the difference between the 4× and the 16×.

**3. Recomputation off.**

*What you find:* it breaks much earlier than expected — typically at sequence lengths or micro-batch sizes that seem modest. From §6.3, activations at micro-batch 1 and 8K are ~172 GB for a 70B model, against 80 GB cards. Recomputation is not an optimization for large models; it is a requirement.

**4. 671B MoE and why EP is mandatory.**

*What you find:* static memory is 10,736 GB (§6.1). To get under 80 GB per GPU by sharding alone you need 134 ranks minimum, and in practice more like 300 with activations and buffers.

ZeRO-3 across a large DP group could technically achieve this — and then every forward pass all-gathers the *full 671B parameter set* per layer, which is catastrophic communication.

**EP is what makes it tractable**, because experts are *naturally* partitioned: expert 47 lives on one GPU and stays there. No all-gather is needed — instead the *tokens* move to the experts, which is a much smaller payload (§6.6: ~470 MB per layer versus 1,342 GB of parameters).

That is the structural insight: **for MoE, move the data to the parameters rather than the parameters to the data.** It is the same trade every distributed system makes, and MoE is unusual in that the parameters are so much larger than the activations that the answer is unambiguous.
