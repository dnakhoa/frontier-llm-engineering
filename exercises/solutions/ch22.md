## 22.1 🔢 The decode floor

**1. Reading the weights once.**

$$\frac{70\times10^9 \times 2 \text{ bytes}}{3.35\times10^{12} \text{ B/s}} = \frac{1.4\times10^{11}}{3.35\times10^{12}} = \mathbf{41.8 \text{ ms}}$$

**2. Batch 1: time per token and utilization.**

**41.8 ms per token** — you must read every weight to produce one token, so the memory read *is* the floor.

FLOPs performed: $2N = 2 \times 70\times10^9 = 1.4\times10^{11}$ per token.

$$\text{achieved} = \frac{1.4\times10^{11}}{0.0418} = 3.35\times10^{12} \text{ FLOP/s}$$
$$\text{utilization} = \frac{3.35\times10^{12}}{990\times10^{12}} = \mathbf{0.34\%}$$

**The tensor cores are 99.7% idle.** This single number explains essentially all of Chapter 22.

**3. Where decode becomes compute-bound.**

At batch $B$, you read the weights once and do $2NB$ FLOPs:

$$I = \frac{2NB}{2N} = B \text{ FLOP/byte}$$

Wait — more carefully. Bytes read is $2N$ (weights in BF16); FLOPs is $2NB$. So $I = B$. Against the ridge point:

$$B \ge \frac{990\times10^{12}}{3.35\times10^{12}} = \mathbf{295}$$

(Chapter 22 §22.2 quotes "$\approx 2B$ FLOP/byte" and a threshold near 150, using a convention that counts both the multiply and the add against the byte; the two conventions differ by a factor of 2 and give thresholds of ~150 or ~295. Either way the answer is *low hundreds*, and that is the number to carry.)

Add the KV cache reads, which grow with $B$ and with context length, and the practical crossover is lower still.

**4. Batch 256.**

Still just below compute-bound. Time per token ≈ 41.8 ms for the weight read, now amortized across 256 sequences:

$$\frac{41.8 \text{ ms}}{256} = \mathbf{0.163 \text{ ms per token per sequence}}$$

Aggregate throughput: $256/0.0418 = \mathbf{6{,}124}$ tokens/s.

**What limits it now:** approaching the boundary. At 256 you are near the ridge, so both memory bandwidth and compute are close to saturated, and the KV cache reads (which scale with $B \times$ context) start to matter as much as the weight reads. Beyond this, adding batch buys compute-bound throughput and costs TPOT.

**5. FP8 helps decode, not prefill.**

**Decode is memory-bound.** Halving the bytes read halves the 41.8 ms floor to ~21 ms. Direct, roughly linear win.

**Prefill is compute-bound** ([Chapter 22 §22.2](../../book/part-4-infra/22-inference-serving.md)) — it processes the whole prompt in parallel, so the arithmetic intensity is matmul-like (thousands of FLOP/byte, per [Exercise 20.1](ch20.md)). The weights are read once and used for many tokens, so their size is not the bottleneck.

Worse: **weight-only** quantization can make prefill *slower*, because you must dequantize to BF16 before the matmul, which is extra work on an operation that was already compute-bound. Only if the tensor cores natively execute FP8 matmuls (Hopper and later) does prefill benefit — and then it benefits from the *compute* speedup, not the memory saving.

## 22.2 🔢 KV cache and concurrency

80 layers, head dim 128, BF16, TP=2.

**1. KV cache per token** ($2 \times L \times H_{kv} \times d_{\text{head}} \times 2$ bytes):

| Scheme | $H_{kv}$ | Per token |
|---|---|---|
| MHA | 64 | $2 \times 80 \times 64 \times 128 \times 2 = \mathbf{2.62 \text{ MB}}$ |
| GQA 8:1 | 8 | $\mathbf{328 \text{ KB}}$ |
| MQA | 1 | $\mathbf{41 \text{ KB}}$ |

**2. Weights per GPU, and remaining HBM.**

$70\times10^9 \times 2 = 140$ GB total, split TP=2 → **70 GB per GPU.**

$$80 - 70 = \mathbf{10 \text{ GB per GPU}} \;\Rightarrow\; \mathbf{20 \text{ GB total across the pair}}$$

(In practice less — CUDA context, activations, communication buffers. Call it 8 GB per GPU realistically; the exercise's 10 is generous.)

**3. Concurrent 8K requests under GQA.**

Cache per request: $328 \text{ KB} \times 8{,}192 = 2.69$ GB. Under TP=2 the cache is also split, so 1.34 GB per GPU.

$$\frac{10 \text{ GB}}{1.34} = \mathbf{7 \text{ concurrent requests}}$$

**4. Concurrent 128K requests.**

Cache per request: $328 \text{ KB} \times 131{,}072 = 43$ GB total, 21.5 GB per GPU.

$$\frac{10}{21.5} = \mathbf{0} \text{ — not even one fits.}$$

You would need TP=4 or more, purely to hold a single long-context request's cache. This is the arithmetic behind [Exercise 1.4](ch01.md)'s conclusion and it is why long-context serving is a different product from short-context serving.

**5. FP8 KV cache.**

Halves the cache: 164 KB/token.

- **8K:** 1.34 GB total, 0.67 GB per GPU → $10/0.67 = \mathbf{14 \text{ concurrent}}$ (double).
- **128K:** 21.5 GB total, 10.75 GB per GPU → still **0**, but now one request fits on 2 GPUs with a little more headroom or a slightly reduced context.

**6. The single change that buys the most concurrency.**

**FP8 KV cache** — it doubles concurrency at every context length, costs a small and usually acceptable quality loss, and requires no architectural change. Chapter 22 §22.6 notes it is under-used, and this is why.

The runner-up is **higher TP degree**, which frees HBM per GPU by splitting the weights further — but it adds an all-reduce per layer to every token (§22.8), so it costs TPOT directly. Use it when you need capacity, not when you need throughput.

The change that would help most and is unavailable to you: **MLA instead of GQA**, which is an architecture decision made at pre-training time and cannot be retrofitted ([Exercise 5.2](ch05.md)).

## 22.3 🔢 Batching and fragmentation

Mean output length: $0.6(100) + 0.3(500) + 0.1(4000) = 60 + 150 + 400 = 610$ tokens.

**1. Static batching, 32 slots.**

A static batch runs until the longest sequence finishes. With 32 samples from this distribution, the maximum is very likely 4,000 (probability at least one of 32 is in the 10% bucket: $1 - 0.9^{32} = 96.6\%$).

Total slot-steps: $32 \times 4{,}000 = 128{,}000$.
Useful slot-steps: $32 \times 610 = 19{,}520$.

$$\text{wasted} = 1 - \frac{19{,}520}{128{,}000} = \mathbf{84.8\%}$$

Nearly six out of seven slot-steps are padding.

**2. Continuous batching.**

A finished sequence's slot is filled immediately by a waiting request, so slots are never idle while work exists.

Waste drops to near zero — bounded only by the scheduling granularity (one token) and by moments when the queue is empty.

$$\text{speedup} \approx \frac{128{,}000}{19{,}520} = \mathbf{6.6\times}$$

This is the single largest win in serving, and it is why §22.4 says every modern engine does it and `model.generate()` does not.

**3. Naive KV allocation, 8K reserved per slot.**

Per request, reserved: $1{,}200 + 8{,}192 = 9{,}392$ tokens' worth (prompt plus max output).
Actually used: $1{,}200 + 610 = 1{,}810$ on average.

$$\text{utilization} = \frac{1{,}810}{9{,}392} = 19.3\% \;\Rightarrow\; \mathbf{80.7\% \text{ of cache reserved and unused}}$$

**4. Paged attention, 16-token blocks.**

Allocation is on demand, so waste is only the partial final block per sequence: on average 7.5 tokens of a 16-token block.

$$\text{waste} = \frac{7.5}{1{,}810} = \mathbf{0.41\%}$$

From 80.7% to under 0.5% — roughly a **4× increase in achievable concurrency** from the memory side alone.

**5. Which to implement first.**

**Continuous batching**, and the reasoning is worth stating.

- It is worth **6.6×** here versus paging's ~4×, on this distribution.
- It is **simpler** — a scheduling change, not a memory-management subsystem.
- Its benefit is **independent of memory pressure**. Paging only helps if you were memory-limited; continuous batching helps even when you have spare HBM.

That said, the two are complementary and the practical answer is "use an engine that has both." Implementing either from scratch, when vLLM and SGLang exist, is almost never the right call — the exercise is about understanding what your engine is doing for you.

## 22.4 🏗️ Serve a reasoning model

**1. Which assumptions break.**

- **"Output length is roughly predictable."** It is not — 8,000 mean with a tail to 60,000 is a 7.5× spread, and the model decides at generation time. You cannot size a batch on expected length.
- **"KV cache is small relative to weights."** At 8,000 output tokens plus prompt, under GQA 8:1, one request's cache is $\sim 3$ GB; at 60,000 it is 20 GB. Cache now rivals or exceeds the weights.
- **"A request occupies a slot briefly."** At 8,000 tokens and ~20 ms/token, a request holds its slot for **160 seconds**; a tail request for 20 minutes. Slot turnover is glacial, which weakens continuous batching's advantage and makes admission decisions much more consequential.
- **"Throughput measures useful work."** Most reasoning tokens are never shown (part 4).

**2. Batching policy, and the tail.**

- **Continuous batching**, still — it is more valuable here, not less, because length variance is extreme.
- **Preempt-and-reschedule for the tail.** Paged attention allows evicting a sequence's blocks and either swapping them to host memory or recomputing later. A 60,000-token request occupying a slot for 20 minutes should be preemptible when short requests are queued.
- **Two pools, by predicted length.** Route requests by a cheap length predictor (prompt characteristics, task type, or an explicit user hint) into a "short" pool with high concurrency and a "long" pool with fewer slots and more cache per slot. This prevents one 60K request from starving 30 short ones — the p99 problem in §22.6 case 3.
- **A hard token cap** with graceful truncation, published in the API. Unbounded generation is not a product.

**3. Best-of-8, and what saves you.**

Naively: 8 full KV caches per logical request. At a 2,000-token prompt and 8,000 output, that is $8 \times 10{,}000 \times 328 \text{ KB} = 26$ GB — one logical request consuming a third of two H100s.

**What saves you: paged attention's copy-on-write prefix sharing** (§22.5). The 8 samples share the prompt's blocks until they diverge:

- Shared prompt: $2{,}000 \times 328 \text{ KB} = 656$ MB, **once**.
- Divergent completions: $8 \times 8{,}000 \times 328 \text{ KB} = 21$ GB.

Saved: $7 \times 656$ MB $= 4.6$ GB, about 18%. Modest here because the completions dominate — but with a 20,000-token prompt and short completions (a document-QA workload) the saving is most of the memory.

This is exactly the [Exercise 13.7](ch13.md) part 2 workload, and it is why an engine without prefix sharing serves reasoning and RL rollouts badly.

**4. Hidden tokens and the throughput metric.**

If the reasoning trace is not shown, you are billing (or paying) for tokens the user never sees. Raw tokens/second stops being the meaningful denominator.

**Report throughput per *useful* token** — per token of final answer — or, better, **requests completed per GPU-hour under the SLO**. A model that reasons for 8,000 tokens to produce a 200-token answer has a 40:1 overhead, and comparing its raw tokens/s against a non-reasoning model's is comparing different things.

The practical consequence: **cost per resolved query** is the metric to optimize, and it makes reasoning-length control ([Exercise 15.6](ch15.md)) a serving concern rather than only a training one.

**5. Disaggregating prefill and decode.**

**For:** the two phases have opposite resource profiles (§22.2), and here that divergence is extreme. Prefill on a 2,000-token prompt is a brief compute-bound burst; decode is 8,000 memory-bound steps. Separate pools let you size each independently, use different TP degrees, and even different hardware. It also prevents a long prefill from stalling every decoding sequence (§22.9's chunked-prefill problem) without needing chunked prefill at all.

**Against:** the KV cache must transfer from the prefill pool to the decode pool. At 2,000 tokens × 328 KB = 656 MB per request, over even a 400 Gb/s link that is ~13 ms — acceptable. But it adds a network dependency to every request, an extra failure mode, and substantial operational complexity for two pools instead of one.

**Verdict:** **yes, at scale.** The decode phase dominates so heavily (8,000 steps versus one prefill) that giving decode its own optimally-configured pool is worth the transfer. At small scale — a handful of GPUs — the complexity is not justified and a single pool with chunked prefill is the right answer.

## 22.5 🔢 Speculative decoding

**1. Draft time for 4 tokens.**

The draft is 70× cheaper per token, so each draft token costs $41.8/70 = 0.597$ ms.

$$4 \times 0.597 = \mathbf{2.39 \text{ ms}}$$

**2. One target forward pass at batch 1.**

**41.8 ms** — verifying 4 tokens costs the same as generating 1, because the weight read dominates and 4 positions is still a tiny batch dimension.

**3. Expected accepted tokens.**

With per-token acceptance $p = 0.7$ and rejection ending the run, the expected number accepted from $k=4$ drafts:

$$\mathbb{E}[\text{accepted}] = \sum_{i=1}^{4} p^i = 0.7 + 0.49 + 0.343 + 0.240 = 1.773$$

Plus the **bonus token**: on a rejection the target resamples the correct token from the corrected distribution, and if all 4 are accepted the target's own forward gives a 5th. So expected tokens produced per cycle:

$$1.773 + 1 = \mathbf{2.77 \text{ tokens}}$$

**4. Speedup.**

Cycle time: $2.39 + 41.8 = 44.2$ ms for 2.77 tokens.

$$\frac{44.2}{2.77} = 15.96 \text{ ms/token} \quad\text{versus}\quad 41.8 \text{ ms/token}$$

$$\text{speedup} = \frac{41.8}{15.96} = \mathbf{2.62\times}$$

Consistent with the 2–3× that §22.7 reports, and note it comes with **no quality change** — the rejection-sampling scheme guarantees the output distribution matches sampling from the target directly.

**5. At batch 256.**

At batch 256 the target is near compute-bound ([Exercise 22.1](ch22.md) part 4). A forward pass over 256 sequences × 4 draft positions is 1,024 positions — now a genuinely large batch, so the target's verification pass costs **substantially more** than a batch-256 single-token step, roughly 4× more since it is compute-bound and doing 4× the FLOPs.

Meanwhile the draft model also runs at batch 256, and its cost no longer disappears.

Rough accounting: verification $\approx 4 \times 41.8 = 167$ ms (compute-bound scaling), draft $\approx 4 \times 256 \times 0.597 / 256 \approx 2.4$ ms amortized but the draft is also memory-bound at its own scale, call it 10 ms. Cycle: ~177 ms for $256 \times 2.77 = 709$ tokens = 0.25 ms/token.

Plain decoding at batch 256: 0.163 ms/token ([Exercise 22.1](ch22.md) part 4).

**Speculative decoding is now ~1.5× *slower*.**

**What happened:** speculative decoding works by **reclaiming wasted compute**. At batch 1, 99.7% of the tensor cores were idle, so verifying 4 tokens was free. At batch 256 there is no waste left — the extra 3 positions per sequence are genuine additional compute, and the draft model's cost is pure overhead.

**The rule:** speculative decoding is a **low-batch, latency-sensitive** technique. Use it for a single interactive user; disable it under load. A serving stack should switch it off automatically above a batch threshold, and one that does not will be slower than plain decoding exactly when it is busiest.

## 22.6 🔢 Diagnose eight serving symptoms

| # | Symptom | Two likely causes | First check |
|---|---|---|---|
| 1 | 8× below a colleague, same hardware | (a) **Static batching**, or `model.generate()` in a loop; (b) no paged attention, so concurrency is capped by reserved cache | Check what engine is running. An 8× gap on identical hardware is almost always continuous batching ([Exercise 22.3](ch22.md) part 2 predicts 6.6×). |
| 2 | OOM at 40 requests, fine at 30, weights use half the HBM | (a) KV cache reserved at max length per slot ([Exercise 22.3](ch22.md) part 3); (b) no paging, so fragmentation | Compute reserved-versus-used cache. If utilization is ~20%, that is it. |
| 3 | p50 TTFT 180 ms, p99 9 s | (a) Long prefills blocking the decode loop — no chunked prefill; (b) no admission control, so long requests starve short ones | Correlate p99 TTFT events with concurrent long-prompt requests. A 50× p50-to-p99 ratio is the signature of head-of-line blocking. |
| 4 | INT4 made prefill 20% slower | **Weight-only quantization on a compute-bound phase** ([Exercise 22.1](ch22.md) part 5) — dequantizing to BF16 adds work | Confirm prefill is compute-bound by computing arithmetic intensity. Then apply quantization to decode only, or use a format with native tensor-core support. |
| 5 | Speculative decoding slower under load | **Batch is large enough to be compute-bound** ([Exercise 22.5](ch22.md) part 5) | Plot speculative-vs-plain throughput against batch size and find the crossover. Then gate speculation on batch size. |
| 6 | Benchmarks dropped 3 points on the serving stack | (a) **Chat-template mismatch** between eval harness and server ([Chapter 11 §11.6](../../book/part-3-post-training/11-sft-frontier-style.md)); (b) different sampling defaults — temperature, top-p, repetition penalty | Dump the exact token ids the harness sends and the server sends for one identical conversation and diff them. It will be whitespace or a missing BOS. |
| 7 | MoE throughput collapses on some batches | **Expert load imbalance** — the all-to-all is synchronous, so one hot expert sets the pace ([Exercise 5.7](ch05.md) part 3) | Log per-expert token counts per batch. A max/mean above ~1.5 explains it. Batch composition determines routing, so it is batch-dependent by nature. |
| 8 | TPOT rises smoothly with concurrency | **Working as designed** — this is the latency/throughput trade-off ([Exercise 22.7](ch22.md)), not a bug | Confirm it is smooth rather than a cliff. If smooth, set a max batch from your SLO. If there is a cliff, look for cache thrashing or preemption. |

Item 8 is on the list deliberately: **not every symptom is a bug.** A serving engineer who "fixes" the latency/throughput trade-off by capping the batch at 4 has traded away most of their capacity to solve a problem that was a design property.

## 22.7 🔢 Goodput

SLO: p95 TTFT ≤ 500 ms, p95 TPOT ≤ 50 ms.

**1. Which meet the SLO.**

| Max batch | TTFT | TPOT | Meets SLO? |
|---|---|---|---|
| 16 | 210 ms ✓ | 22 ms ✓ | **Yes** |
| 32 | 340 ms ✓ | 31 ms ✓ | **Yes** |
| 64 | 620 ms ✗ | 44 ms ✓ | **No** — TTFT |
| 128 | 1,400 ms ✗ | 71 ms ✗ | **No** — both |

**2. Goodput-maximizing choice.**

**Batch 32, at 7,100 tokens/s.** It is the highest throughput among configurations that satisfy the SLO, so it is the highest *goodput*.

Batch 128's 14,200 tok/s is twice the raw throughput and **zero goodput** — none of that traffic is served within the SLO.

**3. Fixing batch 64's TTFT specifically.**

**Chunked prefill** (§22.9).

The mechanism: a long prompt's prefill is split into chunks and interleaved with decode steps, so a decoding batch is never blocked for the full duration of a large prefill. TTFT for *waiting* requests improves because they are no longer queued behind a monolithic prefill.

**What it costs:** TTFT for the *prefilling* request itself gets slightly worse, since its prefill is now spread across several scheduler iterations rather than run at once. You are trading the tail for the median — which is the right trade when the SLO is on p95.

An alternative with a different cost profile: **prefill/decode disaggregation** ([Exercise 22.4](ch22.md) part 5), which removes the interference entirely at the price of a KV-cache transfer and two pools to operate.

**4. Re-evaluating batch 64 after the fix.**

You need to **measure again**, not extrapolate — chunked prefill changes both metrics and the direction of the TPOT change is not obvious.

Specifically measure:

- **p95 TTFT**, to see whether it now clears 500 ms. Expect a substantial improvement for queued requests.
- **p95 TPOT**, which may get *slightly worse* — decode steps now share iterations with prefill chunks, so each decode step is marginally slower. It was 44 ms with only 6 ms of headroom, so a 15% degradation would break the SLO.
- **Throughput**, which may drop a little from the scheduling overhead.
- **The chunk size**, which is the tuning knob: smaller chunks improve TTFT for waiting requests and hurt TPOT more.

The honest possibility: chunked prefill fixes TTFT and breaks TPOT, and batch 32 remains the answer. That is worth knowing before committing to the change.

**5. Why "our throughput is 14,200 tok/s" misleads.**

Because it is a number achieved in a configuration where **no user is served acceptably**. p95 TTFT of 1.4 seconds and TPOT of 71 ms is a visibly slow product.

Raw throughput is trivially gameable: increase the batch until memory runs out, and report the peak. It measures how much work the hardware can do, not how much work you can *sell*.

**Goodput** — throughput subject to a stated SLO — is the number that means something, and quoting it requires quoting the SLO alongside. "7,100 tok/s at p95 TTFT ≤ 500 ms, p95 TPOT ≤ 50 ms" is a claim someone can act on; "14,200 tok/s" is a claim about a configuration you would never run.

Same methodological point as [Chapter 23 §23.4](../../book/part-4-infra/23-evaluation.md)'s on benchmark scores: **a number without its measurement conditions is not comparable to any other number.**

## 22.8 🧪 Break the serving lab

**1. Static versus continuous batching.**

*Prediction:* 2–3×.

*What happens:* **between 3× and 7×, entirely determined by the tail of your
length distribution** — which is the point, and it is worth seeing both numbers.

On the distribution specified in [Exercise 22.3](ch22.md), the arithmetic gives
6.6× and the measurement matches it. The lab generates its own request stream —
lognormal prompts with a 10% long-generation tail, p99/median ≈ 17× — and gets
**3.26×**, squarely inside Chapter 22's quoted 2–4× for realistic traffic.

Neither number is the "right" one. The magnitude surprises people because the
intuition is set by *mean* length while the waste is driven by *maximum* length,
so the ratio is a property of the traffic and not of the scheduler.

Try it with a low-variance distribution (all outputs 500±50 tokens) and the ratio collapses to near 1. **The win is a function of your length variance**, which is the same lesson as [Exercise 11.1](ch11.md)'s packing multiplier.

**2. Naive allocation fragmentation.**

*Prediction:* 50%.

*What happens:* **~80%** ([Exercise 22.3](ch22.md) part 3), because reservation is at max length while use is at mean length, and the ratio is 8,192 to 610.

Worth logging the per-request reserved-versus-used numbers to see the distribution: the 10% of requests generating 4,000 tokens have decent utilization, and the 60% generating 100 tokens have terrible utilization, dragging the aggregate down.

**3. Paged allocation, 16-token blocks.**

*Prediction:* a few percent.

*What happens:* **under 1%** — the only waste is the partial last block, averaging 7.5 of 16 tokens against a sequence of ~1,810 tokens.

The dramatic part is the concurrency change: the same HBM now holds roughly 4× as many requests, which is visible immediately in the lab's throughput number.

**4. Prefix sharing, 8 requests with the same 1,200-token prompt.**

*Prediction:* saves the prompt cache 7 times over.

*What happens:* exactly that — $7 \times 1{,}200 \times 328 \text{ KB} = 2.75$ GB saved, and the lab should report it directly.

The subtlety to observe: the saving **persists only until the sequences diverge**. Watch the shared block count fall as generation proceeds and each sequence writes its own blocks. With a long shared prompt and short completions the saving is durable; with a short prompt and long completions it evaporates quickly — which is [Exercise 22.4](ch22.md) part 3's finding.

**5. Block size 1.**

*Prediction:* zero fragmentation, strictly better.

*What happens:* **fragmentation goes to zero and everything else gets worse.**

- The **attention kernel** must gather from 131,072 scattered locations instead of 8,192 contiguous 16-token blocks. Coalescing is destroyed and effective bandwidth collapses. **This is the binding cost.**
- **Allocation overhead** per token instead of per 16 tokens.
- The **block table** grows 16×, to 131,072 entries per 128K sequence.

That last one is worth calling out because it is the explanation people reach for
and it is not the one that decides the default. The lab sweeps block sizes and
finds the table **negligible in absolute terms at every size** — a fraction of a
megabyte against gigabytes of KV cache. On the bookkeeping alone a 1-token block
looks strictly better than 16, and every production engine disagrees.

The cost that actually sets the default is the scattered gather, and a Python
simulation of allocation cannot see it — you need a profiler. The lab says so
rather than crediting its own arithmetic with the answer.

Net: fragmentation saves ~0.4% of memory and the kernel loses far more in
bandwidth. Sweep 1, 4, 16, 64, 256 and fragmentation is already under 1% by 16
while blocks are still long enough to read efficiently — a shallow optimum around
16–32, which is what engines use.

The general lesson: **the block size trades internal fragmentation against access locality**, and locality wins below 16 because GPUs are built around coalesced access.
