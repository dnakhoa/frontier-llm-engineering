## 14.1 🔢 Derive it yourself

**1. Objective and optimal policy.**

$$\max_{\pi} \; \mathbb{E}_{x,\,y\sim\pi}\big[r(x,y)\big] - \beta\, \mathbb{D}_{\mathrm{KL}}\big[\pi(y|x)\,\|\,\pi_{\mathrm{ref}}(y|x)\big]$$

$$\pi^*(y|x) = \frac{1}{Z(x)}\,\pi_{\mathrm{ref}}(y|x)\exp\!\left(\frac{r(x,y)}{\beta}\right), \qquad Z(x) = \sum_y \pi_{\mathrm{ref}}(y|x)\exp\!\left(\frac{r(x,y)}{\beta}\right)$$

**2. Inverted.**

$$r(x,y) = \beta \log\frac{\pi^*(y|x)}{\pi_{\mathrm{ref}}(y|x)} + \beta \log Z(x)$$

**3. Substitution and cancellation.**

$$r(x,y_w) - r(x,y_l) = \beta\log\frac{\pi^*(y_w|x)}{\pi_{\mathrm{ref}}(y_w|x)} - \beta\log\frac{\pi^*(y_l|x)}{\pi_{\mathrm{ref}}(y_l|x)} + \underbrace{\beta\log Z(x) - \beta\log Z(x)}_{=\,0}$$

**Why it cancels, precisely:** $Z(x)$ is a function of the prompt **only** — it sums over all possible responses to that prompt, so it does not depend on which response you are evaluating. Both $y_w$ and $y_l$ are responses to the *same* prompt $x$, so both carry the *same* $\beta\log Z(x)$ term, and a difference of two identical quantities is zero.

This is the whole trick, and it is worth stating the condition it depends on: **the two responses must share a prompt.** If you tried to compare responses to different prompts, $Z(x_1) \ne Z(x_2)$ and nothing would cancel.

**4. The loss.**

$$\mathcal{L}_{\mathrm{DPO}} = -\,\mathbb{E}_{(x,y_w,y_l)}\left[\log\sigma\!\left(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{\mathrm{ref}}(y_w|x)} - \beta\log\frac{\pi_\theta(y_l|x)}{\pi_{\mathrm{ref}}(y_l|x)}\right)\right]$$

**5. If Bradley-Terry depended on absolute rewards.**

The derivation would collapse. $Z(x)$ would survive, and it is a sum over *every possible response sequence* — an intractable object with no efficient estimator.

You would be back to the situation reward modelling is in: you can learn a function whose *differences* are meaningful, but you cannot recover the normalizing constant, so you cannot express the policy in closed form. DPO exists entirely because Bradley-Terry is difference-based, and that is not a convenience — it is the load-bearing property.

## 14.2 🔢 Compute the loss by hand

**1. Log-ratios.**

$$\log\frac{\pi_\theta(y_w)}{\pi_{\mathrm{ref}}(y_w)} = -42.1 - (-40.3) = \mathbf{-1.8}$$
$$\log\frac{\pi_\theta(y_l)}{\pi_{\mathrm{ref}}(y_l)} = -45.6 - (-41.0) = \mathbf{-4.6}$$

**2. Implicit rewards** ($\beta \times$ log-ratio, $\beta = 0.1$):

$$\hat{r}(y_w) = \mathbf{-0.18}, \qquad \hat{r}(y_l) = \mathbf{-0.46}$$

**3. Logits and loss.**

$$\text{logits} = 0.1 \times (-1.8 - (-4.6)) = 0.1 \times 2.8 = \mathbf{0.28}$$

$$\mathcal{L} = -\log\sigma(0.28) = -\log\!\left(\frac{1}{1+e^{-0.28}}\right) = -\log(0.5695) = \mathbf{0.563}$$

For reference, a completely uninformed model would give $-\log\sigma(0) = 0.693$. So 0.563 is better than chance and not by much.

**4. Getting it right?**

**Yes** — $\hat r(y_w) = -0.18 > \hat r(y_l) = -0.46$, so the implicit reward orders the pair correctly. This pair counts toward the accuracy metric.

But the margin is only 0.28, so $\sigma(0.28) = 0.57$ — the model assigns 57% probability to the correct ordering. It is right, weakly, and this example will still contribute a substantial gradient.

**5. Both log-ratios negative.**

It means the policy has made **both responses less likely than the reference model did.** The policy has moved away from both.

**Is it a problem?** Not from the loss's perspective — the loss only constrains the *difference*, and the difference is correct. This is exactly the §14.6 phenomenon in miniature, observed at a single pair.

It becomes a problem when it is the *systematic* pattern across the dataset, because then the model is becoming less likely to produce the responses you told it were good, and the probability mass has to go somewhere (§14.4). At one pair it is unremarkable; as a training-wide trend it is the central pathology of DPO, and it is why §14.6 insists on logging the two rewards separately rather than only the margin.

## 14.3 🔢 Sum versus average

**1. Averaged log-probabilities.**

$$\bar\ell_\theta(y_w) = \frac{-42.1}{180} = -0.2339, \qquad \bar\ell_{\mathrm{ref}}(y_w) = \frac{-40.3}{180} = -0.2239$$
$$\bar\ell_\theta(y_l) = \frac{-45.6}{60} = -0.7600, \qquad \bar\ell_{\mathrm{ref}}(y_l) = \frac{-41.0}{60} = -0.6833$$

Log-ratios: chosen $= -0.0100$; rejected $= -0.0767$.

$$\text{logits} = 0.1 \times (-0.0100 + 0.0767) = 0.1 \times 0.0667 = \mathbf{0.00667}$$
$$\mathcal{L} = -\log\sigma(0.00667) = \mathbf{0.690}$$

**2. Does the sign change?**

**No** — still positive, so the pair is still ordered correctly. But the magnitude collapsed from 0.28 to 0.0067, a factor of **42×**, and the loss moved from 0.563 to essentially the chance value of 0.693.

Under averaging, this pair now contributes almost the maximum possible gradient (the model is treated as knowing nothing), where under summing it contributed a moderate one.

**3. Why summing disadvantages long responses.**

Every token contributes a negative log-probability. A 180-token response accumulates 180 such terms; a 60-token response accumulates 60. So $\log \pi(y)$ is systematically more negative for longer $y$, **regardless of quality** — a good long response has lower total log-probability than a mediocre short one, essentially always.

In DPO this partly cancels, because the reference model's log-probability is also more negative for the long response. What does *not* cancel is the **variance**: the log-ratio for a 180-token response is a sum of 180 per-token differences, so it has roughly $\sqrt{180/60} = 1.7\times$ the standard deviation of the 60-token one. Long responses produce larger-magnitude log-ratios in both directions, so they dominate the gradient.

**4. Direction of the bias.**

Preference data usually has **longer chosen responses** (annotators prefer thorough answers — the same fact that produces reward-model length bias, §12.6).

So the chosen response is typically the one with the large-magnitude, high-variance log-ratio. When the model gets such a pair right, it gets it very right; when wrong, very wrong. The net effect over training is that **the gradient is dominated by long chosen responses, and the model learns that length is associated with being preferred** — DPO acquires length bias through a different mechanism than PPO, without any reward model being involved.

**5. Which variant addresses it.**

**SimPO** [\[67\]](../../book/appendix/b-references.md#67-simpo), which uses exactly the length-normalized average from part 1, plus an explicit target margin $\gamma$.

**What else it changes:** SimPO also **drops the reference model entirely**. That is a separate decision bundled into the same paper, and it is worth separating — length normalization addresses this exercise's problem; dropping the reference removes the KL anchoring that keeps the policy near a known-good model (§14.7). You can have the first without the second, and if length is your only complaint, length-normalizing DPO while keeping the reference is a smaller, safer change than adopting SimPO wholesale.

SimPO also adds $\gamma$, so the objective demands a *minimum* margin rather than an unbounded one — which addresses a different problem, the one IPO targets.

## 14.4 🔢 The decreasing-logprob phenomenon

**1. Margins.**

- Start: $-0.02 - (-0.03) = \mathbf{+0.01}$
- End: $-0.85 - (-1.94) = \mathbf{+1.09}$

**2. Loss and accuracy.**

Loss at start: $-\log\sigma(0.01) = 0.688$. At end: $-\log\sigma(1.09) = 0.288$.

**Loss decreased by 58%. Accuracy went 51% → 89%.** By every metric on a standard DPO dashboard, this run is a success.

**3. What happened to the chosen responses' absolute probability.**

$\hat r = \beta \log(\pi_\theta/\pi_{\mathrm{ref}})$, so with $\beta = 0.1$:

$$\log\frac{\pi_\theta(y_w)}{\pi_{\mathrm{ref}}(y_w)} = \frac{-0.85}{0.1} = -8.5 \;\Rightarrow\; \frac{\pi_\theta(y_w)}{\pi_{\mathrm{ref}}(y_w)} = e^{-8.5} \approx 2\times10^{-4}$$

**The policy is roughly 5,000× less likely to produce the chosen responses than the reference model was.**

And the rejected: $e^{-19.4} \approx 4\times10^{-9}$ — about 250 million times less likely.

**4. Where the mass went.**

To **everything else** — responses that appear in neither the chosen nor the rejected column.

The mechanism: the DPO loss constrains only the difference. Gradient descent finds the cheapest way to increase the margin, and pushing *down* on a specific, concentrated target (the rejected response) is much easier than pushing *up* on another specific target, because increasing one sequence's probability requires taking mass from everywhere else. The path of least resistance is to reduce both, faster on the rejected one, letting mass diffuse to the unconstrained remainder of the distribution.

**5. Two failure modes, and the confirming metric.**

- **Degenerate or off-distribution generations.** Mass has moved toward sequences neither the reference nor the preference data ever endorsed — which at this magnitude can include repetitive text, truncated responses, or format drift. **Metric:** actually generate from the model and inspect, at every checkpoint. Also track perplexity on a held-out SFT set — if it has risen substantially, the model has moved off the distribution it was trained on.
- **Verbosity / generic drift.** If the mass leaks preferentially toward high-entropy generic continuations, responses get longer and blander. **Metric:** mean response length and a lexical-diversity measure over generations, tracked per checkpoint.

A third worth naming: **capability regression**. Track a capability benchmark against the *SFT model* — the same check §11.11 puts first.

**6. Which variant prevents it, and how.**

**ORPO** [\[66\]](../../book/appendix/b-references.md#66-orpo), most directly.

ORPO's loss is $\mathcal{L}_{\mathrm{SFT}}(y_w) + \lambda\,\mathcal{L}_{\mathrm{OR}}(y_w, y_l)$ — it keeps an explicit **SFT term on the chosen response**. That term is a direct, unconditional push *up* on $\log \pi_\theta(y_w)$, which is exactly the constraint the DPO loss lacks. The chosen response's absolute probability cannot collapse, because there is a term whose only job is to raise it.

**IPO** [\[64\]](../../book/appendix/b-references.md#64-ipo) helps for a different reason: its bounded squared loss around a target margin means once the margin reaches the target, the gradient stops. DPO's logistic loss keeps pushing indefinitely — which is what drives the margin to 1.09 and beyond. IPO removes the incentive to keep separating an already-separated pair, so the drift is smaller.

**SimPO**'s target margin $\gamma$ has a similar bounding effect.

The general shape: DPO's failure here is that **an unbounded objective on a difference is satisfied by driving both terms down**. Every fix either bounds the objective or adds a term that anchors an absolute quantity.

## 14.5 🔢 Memory

**1. Reference model in GPU memory.**

- Policy (trained, mixed precision): $70\times10^9 \times 16 = 1{,}120$ GB
- Reference (frozen, BF16): $70\times10^9 \times 2 = 140$ GB

$$\mathbf{1{,}260 \text{ GB}}$$

**2. Reference log-probabilities precomputed.**

$$\mathbf{1{,}120 \text{ GB}} \text{ — the reference model is not in memory at all.}$$

**3. Storage for precomputed log-probabilities.**

Two floats per pair (summed chosen and rejected log-probabilities), FP32:

$$200{,}000 \times 2 \times 4 = \mathbf{1.6 \text{ MB}}$$

**1.6 megabytes replaces 140 gigabytes.** This is the best trade in Part III and it takes an afternoon to implement: one pass over the dataset with the reference model, store two numbers per pair, never load the reference again.

(If you store *per-token* log-probabilities rather than sums — useful if you might switch to a length-normalized variant later — it is 200,000 × 240 tokens × 4 bytes ≈ 192 MB. Still trivial.)

**4. Versus PPO.**

| Method | Static memory | GPUs (80 GB) |
|---|---|---|
| PPO (70B value) | 2,394 GB | 30 |
| PPO (7B value) | 1,386 GB | 18 |
| RLOO | 1,274 GB | 16 |
| **DPO (reference in memory)** | **1,260 GB** | **16** |
| **DPO (precomputed)** | **1,120 GB** | **14** |

DPO with precomputation needs **less than half** PPO's memory, and — the part the table does not show — it needs **no generation cluster, no weight sync, and no rollout buffer** (§13.10). The operational difference is larger than the memory difference.

## 14.6 🏗️ On-policy or off

**1. Ranking.**

**A > B > C.**

**A (on-policy, human-labelled)** is what the derivation assumes. The pairs are drawn from the distribution the policy actually produces, so the implicit reward is being fit where it will be evaluated.

**B (off-policy, related models, AI-labelled)** works — this is the Zephyr [\[68\]](../../book/appendix/b-references.md#68-zephyr) result and it is why DPO became the open-community default. The generating models are close enough in distribution that the learned preference transfers reasonably.

**C (both responses from a much stronger model)** is the trap, and it is worth being precise about why it is worse than B rather than better.

**2. What DPO actually does with dataset C.**

Your model would never produce either response. So:

- The chosen response has very low probability under your policy. DPO pushes it up — but "up" from $10^{-40}$ is still negligible, and the gradient is dominated by the sheer distance.
- The rejected response *also* has very low probability under your policy, and DPO pushes it down further.
- The margin can be increased almost entirely by pushing the rejected response down, since neither is anywhere near the policy's mode.

The result is that you are not learning a preference. You are performing **a poorly-conditioned form of distillation**, in which the model is told "be less like this GPT-4 output than like that GPT-4 output," when it is not like either.

The practical symptom: §14.4's decreasing-logprob phenomenon, but much worse — both rewards go strongly negative fast, accuracy climbs, and generations degrade.

**3. Mixing a small A with a large B.**

Two approaches, and the second is better:

- **Naive:** mix them by ratio, weighting A higher (say 3–5× per example). Simple, and it dilutes A's on-policy advantage.
- **Better — staged:** run DPO on B first as a broad, cheap improvement, then run a second short DPO pass on A alone at a lower learning rate. B gives coverage; A gives on-policy correction where it counts. This mirrors the general principle that cheap broad data goes first and expensive targeted data goes last, and it is the same shape as [Chapter 9](../../book/part-2-pretraining/09-mid-training.md)'s annealing.

Either way, **re-sample A after the B pass if you can afford it** — because the B pass moved your policy, so your on-policy data is no longer on-policy.

**4. An iterative loop over three rounds.**

```
Round 1:  Sample k responses per prompt from SFT model M0.
          Rank with reward model / judge / verifier.
          Form pairs from best and worst -> D1.
          DPO(M0, D1) -> M1.

Round 2:  Sample from M1 (not M0). Rank. -> D2.
          DPO(M1, D2) -> M2.

Round 3:  Sample from M2. Rank. -> D3.
          DPO(M2, D3) -> M3.
```

Each round's data is on-policy *for that round*, which is the point (§14.8). This is what Llama 3 did, and it is what closes most of the gap with PPO.

Two details that matter:

- **Reset to the SFT model as the reference** each round, or let the reference track the policy? Tracking gives smaller per-round steps and less drift; resetting allows more total movement. Most implementations track, updating $\pi_{\mathrm{ref}} \leftarrow M_{i}$ at each round.
- **Budget:** you have reintroduced generation ($k$ samples per prompt per round), so this costs what RL costs (§13.7). What you keep is the operational simplicity — no value network, no KL controller, no rollout buffer.

**5. Measuring whether off-policy data is hurting.**

The direct measurement: **compute the policy's log-probability of the chosen responses in your dataset, before training.**

- If $\log \pi_{\mathrm{SFT}}(y_w)$ is in the same range as the log-probability of responses the model actually generates → the data is effectively on-policy.
- If it is far lower — many nats per token below the model's typical generations → the data is off-distribution and you are in case C.

Concretely: sample 100 responses from your SFT model, compute their mean per-token log-probability, and compare against the mean per-token log-probability of the dataset's chosen responses. A gap of more than ~0.5 nats/token is a warning.

Two secondary signals, both from §14.4: how fast `chosen_reward` goes negative (faster = more off-policy), and whether held-out SFT perplexity rises during training.

## 14.7 🏗️ Pick a variant

**1. Thumbs-up/down from production.**

**KTO** [\[65\]](../../book/appendix/b-references.md#65-kto). It is the only variant that does not require *pairs* — it takes individually-labelled good/bad responses, which is exactly what a thumbs button produces. Converting thumbs data into pairs requires matching two responses to the same prompt, which production rarely gives you.

**2. Responses 60% longer with no quality gain.**

**SimPO**, for the length normalization (§14.3). Or, more conservatively, keep DPO and switch to length-normalized log-probabilities without adopting SimPO's reference-free design — a smaller change that targets exactly the observed problem.

**3. Near-deterministic preferences, DPO overfits fast.**

**IPO**. This is precisely the case Azar et al. identify: when a preference is deterministic, DPO's logistic loss has no finite optimum — the optimal margin is infinite, so nothing bounds the drift and the KL constraint stops binding. IPO's bounded squared loss around a target margin fixes it by construction.

**4. No SFT stage, one pipeline from base.**

**ORPO**. It folds preference optimization into the SFT loss, so a single run takes you from base model to aligned model with no separate SFT stage and no reference model. That is its entire design purpose.

**5. Memory-constrained, cannot hold or precompute a reference.**

**ORPO or SimPO**, both of which are reference-free.

But check the premise first: per [Exercise 14.5](ch14.md) part 3, precomputing reference log-probabilities costs **1.6 MB** and one pass over the data. "Cannot precompute" is very rarely true, and if it is, the constraint is probably time rather than memory. Going reference-free gives up the KL anchoring that keeps the model near a known-good starting point, which is a real cost to pay for something you likely did not need to pay.

**6. Best-understood, no unusual constraint.**

**DPO.** It has the most implementations, the most debugging experience in the community, the most published results, and the most people who can help when it goes wrong. Per §14.7, the empirical differences between variants are smaller than the difference between on-policy and off-policy data (§14.6) — so spend your effort on the data question, not on the variant question.

## 14.8 📄 Read the DPO paper

**1. The assumption, and where it breaks.**

The derivation assumes the preference data is generated by comparing responses drawn from the **policy being optimized** (or equivalently, that the Bradley-Terry reward being implicitly fit is the reward for *this* policy's distribution).

**Where it breaks:** §14.5's off-policy regime. In offline DPO the data is fixed while the policy moves with every gradient step, so after the first step the assumption is already violated, and it degrades further throughout training. With dataset C ([Exercise 14.6](ch14.md) part 2) it is violated from step zero.

The paper is not silent on this — it discusses the on-policy assumption — but the scale of the practical consequence became clear later, through the iterative-DPO work.

**2. DPO's implicit reward versus an explicit reward model.**

They show the two are equivalent under the derivation: any policy defines an implicit reward $\beta\log(\pi_\theta/\pi_{\mathrm{ref}})$, and fitting the DPO loss is fitting a Bradley-Terry reward model whose parameterization happens to be a language model. The reward model is not eliminated — it is **reparameterized into the policy**.

This has a practically useful corollary the paper notes: you can *use* a DPO-trained model as a reward model, by computing its implicit reward. This is occasionally done and it is a good check on whether the DPO run learned something coherent.

**3. Experimental scale, and extrapolation caution.**

The paper's experiments are at scales well below frontier post-training — sentiment control, summarization, and single-turn dialogue on models in the low billions of parameters.

**What to be careful about:** the tasks are narrow and mostly single-turn; the comparison PPO baselines have the tuning difficulty §14.9 notes (seven hyperparameters, easy to under-tune); and the results do not speak to multi-round iterative use, to verifiable-reward domains, or to the long-horizon regime where §13.8's counterargument bites. The result is real; "DPO ≥ PPO" as a general claim is broader than the evidence.

**4. The decreasing-logprob phenomenon.**

**They do not discuss it.** It was identified later, by practitioners running DPO at scale and looking at the two rewards separately rather than at the margin.

**What that says about how the field learns:** the theory was correct and complete on its own terms — nothing in the derivation is wrong, and nothing in it predicts that constraining a difference would drive both terms down. That behaviour is a property of *gradient descent on this loss with this parameterization*, not of the objective's optimum.

The general lesson, and it recurs throughout Part III: **an objective's optimum and an optimizer's trajectory are different things.** Papers characterize the former; practitioners discover the latter. It is a good argument for logging more than the loss, and for treating "the loss is decreasing" as a much weaker claim than it sounds.

## 14.9 🧪 Break the DPO lab

**1. Matching `trl`.**

The three causes, all in §14.3, in order of frequency:

- **Sum versus mean** over token log-probabilities. `trl`'s `DPOTrainer` sums by default.
- **Prompt masking.** The prompt tokens must be excluded from the log-probability sum, using exactly the same mask as SFT ([Chapter 11 §11.4](../../book/part-3-post-training/11-sft-frontier-style.md)). Including them is the single most common cause of a mismatch, and it is silent.
- **The shift.** Log-probability of token $t$ comes from the logits at position $t-1$. An off-by-one here changes the number without changing the shape.

If it still does not match, check whether the reference log-probabilities were computed with the model in `eval()` mode and under `torch.no_grad()`, and whether dropout was active.

**2. The two rewards separately.**

*Prediction people make:* `chosen_reward` rises, `rejected_reward` falls.

*What happens:* **both fall.** `chosen_reward` declines gently, `rejected_reward` declines steeply, and the margin — the gap between the two curves — widens exactly as intended.

Plotting them on the same axes is the single most useful diagnostic in DPO, and it makes §14.4 immediate rather than abstract. Do this before anything else.

**3. $\beta = 0.01$ versus $\beta = 1.0$.**

The gradient weight per example is $\sigma(-\beta \cdot \text{margin})$.

- **$\beta = 0.01$:** examples essentially never saturate. Even at a margin of 20, the weight is $\sigma(-0.2) = 0.45$ — still nearly half. The policy is pushed far from the reference and both rewards go strongly negative. Fast movement, high drift, more degradation.
- **$\beta = 1.0$:** at a margin of 5, the weight is $\sigma(-5) = 0.0067$ — effectively done. Examples saturate quickly, the policy stays close to the reference, and you may see very little change at all.

The observable: plot the *fraction of the batch with gradient weight above 0.1* over training. At $\beta = 0.01$ it stays high; at $\beta = 1.0$ it collapses within a few hundred steps.

**4. Average instead of summed log-probabilities.**

*Prediction:* generations get shorter.

*What happens:* **generations get shorter**, and the effect is usually clear — often 15–30% on a lab-scale setup. Under summing, the model learns that long chosen responses are associated with large positive margins (§14.3 part 4); normalizing removes that association.

The secondary effect worth noticing: **the loss values change scale dramatically** (§14.3 part 1: 0.563 → 0.690 on the same pair). Your $\beta$ is no longer comparable, and a $\beta$ tuned for summed log-probabilities is far too small for averaged ones. If you switch, retune — SimPO uses a much larger effective $\beta$ for this reason.

**5. Identical chosen and rejected.**

*Prediction:* loss is $\log 2 = 0.693$ and the gradient is zero.

*What happens:* the loss is exactly $-\log\sigma(0) = 0.693$ — correct. But **the gradient is not zero in the way people expect.**

The gradient with respect to the margin is $-\sigma(-0) = -0.5$, the maximum possible. So the loss is pushing hard to increase the margin. But the margin is $\beta[\log\pi_\theta(y_w) - \log\pi_{\mathrm{ref}}(y_w)] - \beta[\log\pi_\theta(y_l) - \log\pi_{\mathrm{ref}}(y_l)]$, and since $y_w$ and $y_l$ are the *same sequence*, the two terms are identical functions of $\theta$ — so their gradients cancel exactly and the parameter gradient is zero.

**Why this matters:** it is exact only when the sequences are byte-identical. If they differ by a single token — a trailing space, different whitespace, one paraphrased word — the cancellation is only approximate, and you get a large gradient (weight 0.5, the maximum) pushing on a distinction that carries no preference information.

This is [Exercise 12.2](ch12.md) part 4's "negligibly better" stratum, appearing in DPO: near-identical pairs contribute maximum gradient weight and zero signal. **Filter them out of your preference data.** A simple edit-distance or embedding-similarity threshold catches them, and removing them is one of the cheapest quality improvements available to a DPO pipeline.
