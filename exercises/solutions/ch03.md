## 3.1 🔢 The funnel

**1. Bytes surviving each stage.**

| Stage | Retention | Surviving |
|---|---|---|
| Raw WARC | — | 100 PB |
| Text extraction | 15% | 15 PB |
| Language filtering | 45% | 6.75 PB |
| Quality filtering | 25% | 1.69 PB |
| Deduplication | 40% kept | **0.675 PB = 675 TB** |

**2. Tokens.**

$$\frac{675 \times 10^{12} \text{ bytes}}{4.2 \text{ bytes/token}} \approx \mathbf{1.61 \times 10^{14} = 161\text{T tokens}}$$

**3. Is that enough?**

Yes — comfortably, by roughly 10×. Which is the point of the exercise: **a single Common Crawl-scale corpus, after aggressive filtering, still has an order of magnitude more tokens than a 15T-token run needs.**

That reframes the whole problem. Data quantity is not the binding constraint at 15T; data *quality* is. You are not scraping to reach a token count, you are filtering to raise a quality bar, and the question is how aggressive you can afford to be.

(If you *were* short, the options ranked by risk to quality: relax the quality threshold — highest risk, it is the stage doing the most work; add more crawls or non-web sources — low risk, high effort; repeat data for more epochs — moderate risk, see §3.3; generate synthetic data — highest variance.)

**4. Which stage to tune first if 30% short.**

**Text extraction**, at 15%. It is the stage with the most headroom and the least quality risk: better boilerplate removal and better handling of HTML, PDFs, and JavaScript-rendered pages recovers *good* text that a crude extractor threw away. Improving extraction from 15% to 20% is a 33% gain in everything downstream, and unlike relaxing quality filters, it does not lower the bar.

The general principle: **when a funnel is short, look for the stage that is discarding good material by accident, not the stage that is discarding bad material on purpose.**

## 3.2 🔢 MinHash economics

**1. Signature matrix memory.**

$$10^{10} \text{ docs} \times 128 \text{ hashes} \times 4 \text{ bytes} = 5.12 \times 10^{12} \text{ bytes} = \mathbf{5.12 \text{ TB}}$$

Too large for one machine, which is why MinHash-LSH at this scale is a distributed job — typically sharded by band, so each worker holds one band's hash table.

**2. Detection probability, $b = 16$, $r = 8$.**

$$P(s) = 1 - (1 - s^8)^{16}$$

| $s$ | $s^8$ | $P$ |
|---|---|---|
| 0.5 | 0.0039 | **0.061** |
| 0.7 | 0.0576 | **0.614** |
| 0.8 | 0.1678 | **0.946** |
| 0.9 | 0.4305 | **0.99997** |

**3. The effective threshold.**

The standard approximation is $t \approx (1/b)^{1/r}$:

$$t \approx (1/16)^{1/8} = 16^{-0.125} = 2^{-0.5} \approx \mathbf{0.707}$$

Which matches the table — $P(0.7) = 0.61$, just past 50%. The S-curve is steep: from 6% detection at $s=0.5$ to 95% at $s=0.8$.

**4. Moving the threshold to 0.7.**

It is already essentially at 0.7 — the exercise's setup gives $t = 0.707$. So the honest answer is "no change needed," and recognizing that is the point.

If you wanted it lower, say $t \approx 0.6$: with 128 total hashes, try $b = 32$, $r = 4$:

$$t \approx (1/32)^{1/4} = 32^{-0.25} \approx 0.42$$

That overshoots. $b = 21$, $r = 6$ gives $t \approx (1/21)^{1/6} \approx 0.60$.

**What it costs:** a lower threshold means more candidate pairs, so more memory for the hash tables, more pairs to verify exactly, and more false positives — documents flagged as duplicates that are merely similar. Since a false positive *deletes real training data*, and §3.1 showed data quantity is not the constraint, erring toward over-deletion is usually the right trade. But it is a trade, and it should be a decision rather than an accident of the default parameters.

## 3.3 🔢 Epochs

**1. Epochs.**

$$\frac{15\text{T}}{8\text{T}} = \mathbf{1.875 \text{ epochs}}$$

**2. Inside the budget?**

Yes, comfortably. Under ~2 epochs is well within the range where repeated data behaves close to fresh data.

**3. Bigger model versus more epochs.**

- **Option A** — 15T tokens: at 20 tokens/parameter, Chinchilla-optimal is $15\times10^{12}/20 = \mathbf{750\text{B parameters}}$.
- **Option B** — 8T unique tokens, one epoch, same compute budget. Same total token-parameter product, so a similar arithmetic answer, but with fewer tokens the compute-optimal split shifts toward a *larger* model on *less* data: roughly $8\times10^{12}/20 = \mathbf{400\text{B parameters}}$ at Chinchilla, with the leftover compute going into a larger model still.

**Which to pick for a model you will serve heavily?** Neither, as stated — and that is the real answer.

Chinchilla optimizes *training* compute for a given loss. If you are going to serve the model to millions of users, inference cost dominates the lifetime bill, and you should deliberately train a **smaller model on more tokens** than Chinchilla suggests. This is §8.11's argument and it is why Llama-3-8B was trained on 15T tokens — roughly 1,900 tokens per parameter, about 95× past Chinchilla.

So the correct answer is: **train on all 15T tokens, and pick the model size from your inference budget rather than from a training-compute optimum.** The 1.875 epochs is fine.

**4. Two ways to get more unique tokens.**

- **More non-web sources** — books, papers, code repositories, transcripts, PDFs. Risk: licensing, and a distribution shift toward formal text that can make the model worse at conversational registers.
- **Synthetic generation** — rephrasing, or model-generated content. Risk: it can only recombine what the generating model knows (§26.4), and it launders benchmark contamination invisibly (§23.5). This is the higher-variance option and it is increasingly used anyway.

## 3.4 🏗️ Design a mixture

A defensible 6T-token mixture:

| Source | Tokens | Share | Factor vs natural abundance |
|---|---|---|---|
| English web (filtered) | 1,800B | 30% | **0.3×** — downsampled hard; it is the most abundant and the least dense per token |
| Code (permissive licences) | 1,200B | 20% | **4×** — upsampled; the brief demands strong code, and code improves reasoning generally |
| Chinese/other multilingual web | 600B | 10% | ~1× |
| Vietnamese | 480B | 8% | **~15×** — see part 3 |
| Japanese | 480B | 8% | **~8×** |
| Math (papers, problems, proofs) | 420B | 7% | **20×** — scarce and high-value |
| Books | 420B | 7% | **5×** — long-form coherence, hard to get elsewhere |
| Academic papers | 360B | 6% | **6×** |
| Reference (encyclopedic, curated) | 240B | 4% | **10×** |
| **Total** | **6,000B** | | |

**3. The multilingual epoch problem — the important part.**

High-quality filtered Vietnamese web text is plausibly on the order of 30–60B tokens. To reach 480B you need roughly **8–16 epochs** of it. Japanese is better-resourced; call it 150–250B available, so 2–3 epochs.

Vietnamese at 8–16 epochs is well past the ~4-epoch guidance from §3.3. Consequences: the model memorizes rather than generalizes on Vietnamese, and Vietnamese quality plateaus long before the token budget is spent.

**Mitigations, in order of preference:**

- **Widen the Vietnamese source set** aggressively — books, subtitles, government and legal documents, forums, translated technical material. Lower the quality bar for Vietnamese specifically, because for a scarce language the marginal mediocre document beats the marginal repeat.
- **Accept a lower share.** 300B at 5–10 epochs may produce a better Vietnamese model than 480B at 16.
- **Translate into Vietnamese** from English. Cheap volume, and it produces translationese — the model learns Vietnamese-as-relexified-English. Use sparingly and never as the majority.

The general rule worth extracting: **for a scarce language, the constraint is not your budget, it is the supply.** Allocating tokens you cannot fill with distinct data is allocating epochs.

**4. The code ablation.** Train three 1–3B models identical except for code share (10%, 20%, 30%), evaluate on HumanEval/MBPP *and* on English and reasoning benchmarks. **What would change my mind:** if 30% code costs more than ~1.5 points of English quality for less than ~3 points of HumanEval, drop to 15%. The point of the ablation is to price the trade, not to find "the best code number."

**5. Most-likely-wrong decision.** The Vietnamese share, for exactly the reason in part 3 — it is the one where the plan may be unachievable rather than merely suboptimal.

**How to find out early:** before committing, *count the tokens you actually have* after filtering, per language. This is a data-engineering task that takes days, not a training run that takes weeks, and it converts the riskiest assumption in the mixture into a measured fact. Do this before writing the mixture table, not after.

## 3.5 🏗️ Rank the filters

| Filter | Removes | Wrongly removes | Typical drop |
|---|---|---|---|
| 1. Language ID threshold | Wrong-language and gibberish pages | Code-switched text, short documents (langID is unreliable under ~50 words), dialects and low-resource languages misclassified as their high-resource neighbours | 10–30% |
| 2. Length minimum | Stubs, navigation pages, error pages | Legitimately short content: definitions, Q&A answers, poetry | 20–40% |
| 3. Mean words per line | Navigation menus, link farms, tables of contents | Code, poetry, subtitles, structured data, chat logs | 5–15% |
| 4. Symbol-to-word ratio | Corrupted extraction, spam, math-symbol soup from bad PDF parsing | **Actual mathematics**, code, chemistry, and any technical notation | 3–10% |
| 5. Repeated-line fraction | Boilerplate, headers/footers, spam | Song lyrics, legal boilerplate that is genuinely the content, logs | 5–15% |
| 6. Learned quality classifier (Wikipedia-vs-web) | Low-information web text | **Anything not written in an encyclopedic register** — forums, informal writing, dialect, non-standard varieties | 50–80% |
| 7. Toxicity classifier | Harmful content | Discussion *about* harm, medical and legal content, reclaimed language, and — well documented — African-American English at substantially higher rates | 1–5% |
| 8. Benchmark n-gram decontamination | Verbatim test items | Legitimate text that happens to share an n-gram; misses paraphrase entirely (§23.5) | <1% |

**The two to be most reluctant about: 6 and 7.**

**Filter 6** is the highest-leverage and highest-risk filter in the pipeline. A Wikipedia-vs-web classifier does not measure "quality"; it measures *similarity to Wikipedia's register*. Applied aggressively it strips conversational, regional, and informal writing — which is most of how people actually communicate, and therefore most of what an assistant needs to understand. It also disproportionately removes text by and about groups under-represented in the reference corpus.

**Filter 7** has the most directly documented demographic side effect: toxicity classifiers flag African-American English at markedly higher rates than Standard American English for equivalent content. Running it aggressively at the pre-training stage removes a dialect from the model's competence, which then shows up as worse performance for those speakers at every downstream stage.

**Filter 4** deserves a mention for a different reason: it is the one that quietly deletes your math corpus. Anyone who has aggressively symbol-filtered a crawl and then wondered why math performance is poor has met this.

**The general principle:** every filter has a false-positive class, and the false positives are systematically *not random*. Knowing what each filter deletes by mistake is more important than knowing what it deletes on purpose.

## 3.6 📄 Read a data card

Working from the chapter's summary of Llama 3 (§3.5), and confirmable in the paper:

**1. Mixture.** Roughly 50% general web/knowledge, 25% code and reasoning, ~10% multilingual, ~7.5% academic/scientific. Chosen through scaling-law experiments on smaller models — they trained small models on candidate mixtures and extrapolated, which is the mixture-ablation methodology §3.4 part 4 asks you to design.

**2. Deduplication.** Multiple granularities: URL-level, document-level via MinHash, and line-level within documents. The line-level pass is the one people skip and it removes boilerplate that survives document-level dedup.

**3. Decontamination.** Reported against a substantial set of benchmarks (the chapter cites 32), with the methodology described. Note this is n-gram based and therefore subject to §23.5's limits.

**4. Three things needed to reproduce, that are not given.**

- **The quality classifier itself** — its training data, its architecture, and its threshold. This is the single most load-bearing undisclosed component.
- **The exact source list and URL-level filtering rules.** "Web data" covers a very wide range of possible corpora.
- **The scaling-law experiment details** that produced the mixture — which candidate mixtures were tested, at what sizes, and what the fitted curves looked like.

Same pattern as §19.8: **what is withheld is the data pipeline, not the architecture.**

## 3.7 🧪 Break the dedup lab

**1. 128 → 32 permutations.**

*Prediction people make:* recall drops.

*What happens:* the *variance* of the Jaccard estimate rises sharply — the
standard error of a MinHash estimate scales as $1/\sqrt{k}$, so going from 128 to
32 doubles it, and the lab's measured error tracks that theory closely. The
S-curve around the threshold gets much less sharp, and near-duplicates at
$s \approx t$ become close to coin flips.

**Recall is what degrades.** The lab measures it falling from 89.5% to 69.9%.
Precision does *not* necessarily fall with it — in the lab it rises, from 82.8%
to 92.6%, because you cannot change $k$ without also changing the available
$(b, r)$ factorisations, and a 32-permutation signature admits only stricter
bandings. Cutting $k$ moved the threshold as well as blurring it, which is a
useful reminder that these two knobs are not independent.

The point: MinHash quality is about the *sharpness* of the threshold, not just
its position — and if you want to isolate sharpness from position you have to
hold $(1/b)^{1/r}$ fixed while you vary $k$, which is a good exercise on its own.

**2. (16, 8) → (32, 4).**

*Prediction:* the threshold moves down. Correct.

$$t \approx (1/32)^{1/4} \approx 0.42$$

versus 0.707 before. Far more aggressive — you will now flag documents that share less than half their content. More candidate pairs to verify, more memory, and more real data deleted.

**3. Quality classifier on an out-of-domain corpus.**

*Prediction people make:* it scores them neutrally, around the middle.

*What happens:* **it depends on what kind of "out of domain" you mean, and the lab
separates the two.**

Hold an entire *topic* out of training — same register, same length, same
formatting, unseen subject matter — and the classifier keeps almost all of it:
84–90% survive the cut. Topic transfer largely works. The slogan "a quality
classifier is really a domain classifier" is too crude.

Change the *genre* and it collapses. Source code and contract text are rejected
outright, at the same quality and the same length as the prose that is kept.

The mechanism is narrower and more actionable than a general
out-of-distribution story: **the classifier deletes what the negative class
taught it to delete, plus whatever shares that surface form.** Raw crawl contains
code and legal boilerplate, so those land in the negative class, so they get
deleted. Nothing about them is lower quality.

Which means the negative class *is* the corpus policy. Every decision about what
counts as junk is encoded there, made once by whoever assembled the training
set, and written down nowhere. That is a policy document disguised as a dataset,
and it is why §3.5 says to read what a lab put in its negative class rather than
the accuracy it reports.

The practical check is unchanged and still worth doing: for any source category
in your corpus, look at its score distribution specifically. Just expect the
failures to sort by register, not by subject.

**4. Dedup after filtering instead of before.**

*Prediction:* the final corpus is the same, just computed in a different order.

*What happens:* **it is not the same**, and the difference matters.

Deduplication does not merely *remove* documents — it **elects a representative**
from each cluster of near-duplicates, and that is why the two orders differ.

The direction is the opposite of the intuitive one. Dedup-first elects a
representative before knowing anything about quality; if the elected document is
the one the filter later rejects, **the entire cluster is lost**, including
siblings that would have passed. Filter-first removes the bad members while the
cluster is still intact, so a clean sibling gets elected instead. So filter-first
keeps *more* documents, not fewer: the lab measures 311 against 300, with 11
clusters surviving only under filter-first.

The practical consequence: **dedup-first is cheaper, filter-first is more
complete.** The cost difference is the real reason production deduplicates first
— the quality classifier runs on every surviving document, so dedup-first is the
difference between scoring $10^{10}$ documents and $10^9$ (the lab's counter
shows 389 against 562 on its corpus). The standard repair is to keep the cost
ordering and remove the defect: make the election **quality-aware**, keeping the
highest-scoring member of a cluster rather than the first one seen.

The general lesson: **pipeline stage ordering changes the output, not just the cost.** These stages do not commute, and treating them as if they do is a common design error.

## 3.8 🔢 The storage bill

**1. Tokenized corpus as `uint32`.**

$$15 \times 10^{12} \text{ tokens} \times 4 \text{ bytes} = 60 \times 10^{12} \text{ bytes} = \mathbf{60 \text{ TB}}$$

(Compare: the raw text at 4.2 bytes/token is 63 TB, so `uint32` token IDs are essentially the same size as the text. This surprises people.)

**2. `uint16` instead.**

Requires a vocabulary of at most 65,536 tokens. Modern vocabularies are typically 32K–256K, so a 32K or 64K vocabulary fits and a 128K+ one does not.

Saves exactly half: **30 TB**. This is a real consideration in vocabulary-size selection (§4.4) that rarely makes it into the discussion, alongside the embedding-parameter and fertility trade-offs.

**3. Required read bandwidth.**

From [Exercise 1.2](../ch01.md), aggregate throughput was ~3.02M tokens/s. At 4 bytes per token:

$$3.02\times10^6 \times 4 = \mathbf{12.1 \text{ GB/s}}$$

**4. Is that achievable, and what is the standard architecture?**

12 GB/s aggregate is modest for a serious parallel filesystem — Lustre or GPFS at this scale delivers far more. So the raw number is not the problem.

The problem is the *access pattern*. 2,048 ranks each opening files, seeking, and reading small shuffled records generates enormous metadata load, and metadata operations are what kill shared filesystems long before bandwidth does.

**The standard architecture:**

- **Pre-tokenize and pre-shuffle offline** into large sequential shard files (typically 100 MB–1 GB each). No per-sample seeking at training time.
- **Assign shards to ranks**, so each rank reads a disjoint set sequentially. No contention, no coordination.
- **Prefetch several shards ahead** into host memory, overlapping I/O with compute.
- **Cache aggressively on local NVMe.** At 60 TB across 256 nodes, that is under 250 GB per node — a single local drive. After the first epoch, the shared filesystem is barely touched.
- **Keep the loader's position in the checkpoint** (§21.6), which is what makes the shard assignment resumable.

The takeaway: **the data loader is a systems component, not a utility function.** At this scale it is the difference between a run at full throughput and a run where 2,048 GPUs wait on metadata.
