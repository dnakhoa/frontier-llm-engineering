## 20.1 🔢 ★ Arithmetic intensity, every operation

A transformer layer with $d = 8192$, $d_{\text{ff}} = 28672$, batch × sequence = 8192 tokens, BF16. For each operation compute FLOPs, HBM bytes moved, and arithmetic intensity, then classify against the H100 ridge point of ~295 FLOP/byte.

1. The FFN's first matmul, $(8192, 8192) \times (8192, 28672)$.
2. RMSNorm over the $(8192, 8192)$ activation.
3. SwiGLU's elementwise product on $(8192, 28672)$.
4. The residual add on $(8192, 8192)$.
5. RoPE application to Q and K.
6. Rank them by how much fusion would help.

## 20.4 🏗️ ★★ Benchmark critique

A colleague reports: "My fused RMSNorm kernel is 4.2× faster than PyTorch."

```python
import time
start = time.time()
for _ in range(1000):
    out = my_rmsnorm(x, w)
print(f"{(time.time() - start) / 1000 * 1000:.3f} ms")
```

with `x = torch.randn(4096, 4096, device='cuda', dtype=torch.bfloat16)`.

1. Name four things wrong with this measurement.
2. Rewrite it correctly.
3. What baseline should they have compared against, and why is `torch.rmsnorm` or a naive PyTorch implementation the wrong one?
4. What should they report instead of a speedup ratio?
5. What shapes should they sweep, and what would you expect to see at the edges?

## 20.6 🏗️ ★★ When to write a kernel

For each, decide: leave it to PyTorch, use `torch.compile`, write Triton, or write CUDA. Justify.

1. A chain of five elementwise operations on a large tensor.
2. Fused RMSNorm + QKV projection.
3. MoE dispatch: gather tokens by expert assignment, run per-expert GEMMs of varying sizes, scatter back.
4. An attention variant with a novel masking pattern.
5. FP8 GEMM with per-block scaling on Hopper.
6. A custom loss function with an unusual reduction.
