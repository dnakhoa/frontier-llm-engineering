## 11.1 🔢 ★ The packing win

Your SFT set has 800,000 examples. The length distribution, in tokens:

| Percentile | Length |
|---|---|
| 50th | 380 |
| 90th | 1,900 |
| 99th | 7,100 |
| max | 31,000 |

Mean length is 720 tokens. You train at a 8,192-token context.

1. If you pad every example to 8,192, how many tokens does one epoch process?
2. How many of those tokens are real content?
3. If you pack perfectly (no waste except the tail of each pack), how many tokens does one epoch process?
4. What is the speedup, and what happens to it if you drop the 1% of examples longer than 8,192?

## 11.2 🔢 ★★ Epoch budget

You are fine-tuning a 70B dense model. The SFT set is 1.2M examples averaging 720 tokens. You train for 3 epochs with packing at 8,192 context.

Assume the standard $6ND$ approximation for training FLOPs (forward + backward, $N$ parameters, $D$ tokens).

1. How many tokens does the full SFT run process?
2. How many FLOPs is that?
3. On 64 H100s at 40% MFU (H100 BF16 dense peak ≈ 990 TFLOP/s), how long does the run take?
4. The pre-training run for this model processed 15T tokens. What fraction of the pre-training compute is the SFT run?

Part 4 is the point of the exercise. Write down your expectation before you compute it.

## 11.3 🔢 ★★ Where did the supervision go?

A conversation has 6 turns (3 user, 3 assistant). Token counts:

| Turn | Role | Content tokens |
|---|---|---|
| 1 | user | 40 |
| 2 | assistant | 120 |
| 3 | user | 25 |
| 4 | assistant | 200 |
| 5 | user | 60 |
| 6 | assistant | 150 |

Each turn also carries 1 role-marker token, and each assistant turn ends with 1 `<|end|>` token.

Compute the number of tokens that contribute to the loss under each masking scheme:

1. Correct masking.
2. `no_mask` — everything is a target.
3. `last_turn` — only the final assistant turn is learned.
4. `no_eos` — correct, except `<|end|>` is excluded.

Then: for scheme 3, what fraction of the correct supervision survives? If your dataset averages 6 turns, how much of your annotation budget did that bug waste?

## 11.4 🏗️ ★★ Design an SFT mixture

You are building the SFT mixture for a 30B general-purpose model. Constraints:

- Budget: 600,000 examples total.
- The model must be strong at code and competent at math.
- It ships in English, Vietnamese, and Japanese.
- It supports 128K context and tool calling.
- Legal has required refusal behaviour on four sensitive categories.
- Product has told you responses are "too long" in the previous generation.

Produce:

1. A mixture table with example counts per category, summing to 600,000.
2. For each category, where the data comes from (§11.3's four sources).
3. Three capability trade-offs your mixture makes, and which side you chose.
4. The single ablation you would run first if you could only run one.
5. How you address the "too long" feedback *in the SFT stage specifically*, and why doing it here is better or worse than doing it in RL.

2. The model works in the eval harness and is measurably worse in the product, on identical prompts.

## 11.6 🔢 ★★ Rejection sampling economics

You have 200,000 prompts. For each you will sample $k$ responses from a 70B model, score them with a 7B reward model, and keep the best.

Assumptions: mean response 600 tokens; generation runs at 2,400 tokens/sec/GPU for the 70B model at your batch size; reward scoring costs 1/20th of generation per response; you have 128 H100s.

1. For $k = 8$, how many GPU-hours does one rejection-sampling round cost?
2. For $k = 64$?
3. Chapter 11 says rejection sampling only reinforces what the model already does sometimes. If a prompt has a 2% chance of a correct response per sample, what is the probability at least one of $k=8$ samples is correct? At $k=64$?
4. Given your answer to 3, argue for or against spending the $k=64$ budget rather than running 8× more prompts at $k=8$.

## 11.10 🏗️ ★★★ The template migration

You shipped a model six months ago with this template:

```
<|system|>{system}<|end|>
<|user|>{content}<|end|>
<|assistant|>{content}<|end|>
```

The new generation needs tool calls. The proposal is:

```
<|system|>{system}<|end|>
<|user|>{content}<|end|>
<|tool_result|>{content}<|end|>
<|assistant|>{content}<|end|>
<|tool_call|>{json}<|end|>
```

Third-party developers have hardcoded the old template in their inference stacks. You cannot force them to update.

1. What breaks if a client using the old template calls the new model?
2. What breaks if a client using the new template calls the old model?
3. Design a migration that does not break existing clients. State explicitly what you give up.
4. Two new special tokens must be added to the vocabulary. What happens to their embeddings at initialization, and what would you do about it?
5. Is there a version of this problem you could have avoided entirely with a decision made before the first model shipped?
