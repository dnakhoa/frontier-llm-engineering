## 1.1 🔢 ★ The compute bill

DeepSeek-V3 reports 2,788,000 H800 GPU-hours on 2,048 GPUs for its full training, of which 2,664,000 were pre-training [\[1\]](../book/appendix/b-references.md#1-deepseek-v3).

1. How many days of wall-clock is the pre-training, assuming all 2,048 GPUs were busy the whole time? Compare with the report's "less than two months".
2. At a rental price of $2.00 per H800-hour, what is the compute cost? Compare to the $5.576M the team reports.
3. The reported figure covers the final training run only. Name three substantial cost categories it excludes, and say whether each is likely larger or smaller than the run itself.

## 1.2 🔢 ★★ Tokens per second, and whether the numbers hang together

Same run's pre-training: 14.8T tokens, 2,664K H800 GPU-hours, 37B active parameters per token.

1. What is the aggregate training throughput in tokens/second?
2. Per GPU?
3. Using the $6ND$ approximation with $N$ = **active** parameters, how many FLOPs did the run consume?
4. An H800 does roughly 990 TFLOP/s of dense BF16. What MFU does your answer to 3 imply — and why is that number misleading for this particular run?

Part 4 is the point. Write down what you expect before computing it.

## 1.3 🔢 ★★ Where 671B parameters live

DeepSeek-V3 has 671B total parameters, 37B active per token.

1. In BF16, how much memory do the weights alone occupy?
2. Using the 16 bytes/parameter figure for mixed-precision AdamW training, how much static state does the full model require?
3. On 2,048 H800s with 80 GB each, what fraction of total cluster HBM is that?
4. Why can you not simply divide by 2,048 and declare it comfortable? Name two things that consume the rest.

## 1.4 🔢 ★★ The MLA claim

Chapter 1 states that MLA reduces KV cache memory by about 93% relative to standard MHA.

1. If a model's MHA KV cache is 2.5 MB per token, what is the MLA cache per token under that claim?
2. At 128K context, how much cache does each approach need for a single sequence?
3. An H800 has 80 GB. Ignoring model weights entirely, how many 128K-context sequences fit under each scheme?
4. Explain in one sentence why this is an *architecture* decision that a serving team cares about more than a training team.

## 1.5 🏗️ ★★ Read the run backwards

You are handed only these facts about an unfamiliar training run:

- 512 GPUs, 21 days, 8T tokens
- Dense model, not MoE
- BF16, no FP8
- Context length 8,192 throughout
- Checkpoints every 45 minutes

1. Estimate the model size, stating your assumptions.
2. What is the implied MFU? Is it plausible?
3. Name three things you would immediately want to check about this run's health.
4. The checkpoint interval is 45 minutes. Using Chapter 21's $\sqrt{2 C \cdot \text{MTBF}}$ result and a cluster MTBF you estimate from the GPU count, is that interval too long, too short, or about right?

Part 4 requires a chapter you have not read yet. Attempt it anyway — the estimate matters more than the formula.

## 1.6 🏗️ ★ The one-page summary

Without looking at the chapter, write the DeepSeek-V3 run as a single paragraph covering: model size and sparsity, data scale, cluster, duration, the four architectural choices that made it unusual, and the precision format.

Then check. What did you leave out, and is what you left out load-bearing or decorative?

## 1.8 🔢 ★★★ The failure budget

The chapter notes that a run of this scale experiences hardware failures regularly.

1. Assuming a per-GPU MTBF of 50,000 hours, what is the expected time between GPU failures across 2,048 GPUs?
2. Over a 60-day run, how many GPU failures should you expect?
3. If each failure costs 25 minutes (detect, reschedule, reload, redo lost work), what fraction of the run is lost?
4. Meta reported 419 unexpected interruptions over 54 days on 16,384 GPUs (Chapter 21 §21.1). Does that rate agree with your model? If not, what is your model missing?

Part 4 is the one worth doing carefully.
