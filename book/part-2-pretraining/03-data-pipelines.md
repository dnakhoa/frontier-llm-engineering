# Chapter 3: Trillion-token data pipelines

> Reading time: ~35 minutes. This is the deepest chapter on data pipelines you'll find outside an industry lab. By the end, you should be able to read any frontier lab's data card and understand every line.

*Current as of early 2025.*

## 3.1 Why data is the model

A pre-trained language model is, in a precise sense, a compressed representation of its training data. Given enough parameters and enough training, you can recover surprising amounts of the training data verbatim from the model (Carlini et al., 2021 [\[4\]](../appendix/b-references.md#4-extracting-training-data)). Given less, the model still encodes statistical regularities of the data — facts, reasoning patterns, code idioms, language biases.

The implications are sharp:

- **Data quality is a hard upper bound on model quality.** No architecture or optimizer can recover information that was not in the data.
- **Data quantity matters, but with diminishing returns.** Scaling laws (Chapter 8) tell you the relationship between data, parameters, and compute. For most labs, the constraint is now compute and data curation, not raw data quantity.
- **Data mix matters enormously.** A model trained on 100% web text will be very different from one trained on 50% web + 25% code + 15% math + 10% books. The mix determines what the model is good at.
- **Data is not static.** A frontier run iterates on the data mix during training, often multiple times. The data pipeline is not a "build it once" system.

This chapter walks through the entire pipeline, from raw crawl to packed training sequences.

## 3.2 The raw sources

A frontier pre-training corpus is a mix of multiple sources. The exact mix varies by lab, but the categories are remarkably consistent.

### 3.2.1 Web text (Common Crawl and beyond)

The single largest source is web text, almost always starting with **Common Crawl** — a non-profit that has been crawling the web since 2008 and releases snapshots every 1–2 months. Each snapshot is ~200–400 TiB of raw WARC (web archive) data, containing HTML, HTTP headers, and metadata.

Frontier labs do not just use Common Crawl directly. They typically also crawl additional sources:
- Top sites ranked by traffic (e.g., top 1M domains by Tranco or SimilarWeb rank).
- Specific verticals: news sites, forums (Reddit, StackExchange), encyclopedias (Wikipedia), Q&A sites.
- Code-hosting platforms (GitHub, GitLab).
- Academic sources (arXiv, PubMed, Semantic Scholar).

The volume is enormous. The DeepSeek-V3 paper [\[1\]](../appendix/b-references.md#1-deepseek-v3) reports their pre-training corpus as 14.8T tokens. The Llama-3 paper [\[5\]](../appendix/b-references.md#5-llama-3) reports 15.6T tokens. The Qwen3 paper [\[6\]](../appendix/b-references.md#6-qwen3) reports about 36T pre-training tokens, covering 119 languages and dialects ([fact sheet](../appendix/fact-sheets/qwen3.md#pre-training-data)). The web is the dominant source for all of these.

### 3.2.2 Code

Code is treated as a first-class data source, not a footnote. Frontier models are typically trained on tens to hundreds of billions of tokens of code.

Sources:
- **GitHub** — public repositories. Deduplicated by repository, filtered by license (MIT, Apache 2.0, BSD, etc.; no GPL unless explicitly allowed), filtered for quality (stars, recent activity, no obvious test repos).
- **GitLab**, **Bitbucket** — smaller but still meaningful.
- **StackOverflow** — Q&A in many programming languages, with high signal-to-noise.
- **Issue trackers and PRs** — useful for understanding the development process, though often excluded for being too low-signal.
- **Synthetic code** — generated by previous models, filtered for correctness via execution or test cases. This is increasingly important.

Code-specific processing is non-trivial. HTML in Jupyter notebooks, line numbers, comments in mixed languages, multiple encodings (UTF-8, Latin-1, Shift-JIS for Japanese comments), and the need to preserve structure (indentation, brackets) all matter.

A particularly thorny issue is **license filtering**. Different labs have different policies. Some (Meta with Llama, DeepSeek) filter to permissive licenses. Others (Alibaba with Qwen) are more permissive. The choice has implications for the commercial usability of the resulting model.

### 3.2.3 Books

Books are high-quality, long-form, well-edited text. They are valuable for the model but small in volume relative to web text.

Sources:
- **Public domain books** (Project Gutenberg, Standard Ebooks).
- **LibGen-style collections** — almost every frontier lab has used these at some point, with varying degrees of public acknowledgment. The legal and ethical status is debated.
- **Internet Archive** — borrowed book collections.
- **Smaller curated corpora** (BookCorpus, which is now mostly subsumed by larger sources).

The 2023–2024 trend has been toward more careful book inclusion: smaller volumes, more curation, more attention to source quality. The Llama-3 paper, for example, reports including books from "a larger, more carefully curated corpus" relative to Llama-2.

### 3.2.4 Scientific and academic text

Sources:
- **arXiv** — preprints in CS, math, physics, etc. LaTeX source, which preserves equations.
- **PubMed / PubMed Central** — biomedical literature.
- **Semantic Scholar** — a curated academic corpus.
- **Specific conference proceedings** (NeurIPS, ICML, ICLR).

The value of academic text is that it is dense, well-written, and contains reasoning patterns the model can learn. The challenge is that LaTeX source is messy: macros, citations, equations, tables. Parsing it correctly is itself a non-trivial engineering problem.

### 3.2.5 Multilingual text

Frontier models are increasingly multilingual. The Qwen models are particularly strong on Chinese; DeepSeek-V3 is heavily bilingual (English + Chinese). Llama-3 supports 8 languages. The data pipeline has language identification at multiple stages.

Multilingual sources include:
- **mC4** (multilingual C4) — a Common Crawl-derived multilingual corpus.
- **CCAligned**, **Multi30k**, and similar aligned corpora.
- **Wikipedia** in many languages.
- **Country-specific crawls** (e.g., Chinese web via a different Common Crawl mirror).
- **Native-language code repositories** (Chinese GitHub, Japanese Qiita).

The data mix is heavily English-weighted even at multilingual-focused labs. DeepSeek-V3's reported mix is roughly 60% English, 30% Chinese, 10% other. Qwen3 publishes no language split at all, only that its corpus covers 119 languages and dialects ([fact sheet](../appendix/fact-sheets/qwen3.md#pre-training-data)). The exact ratios are trade secrets; at most, a lab publishes the directional split.

### 3.2.6 Math, instruction data, and synthetic data

The remaining categories are smaller but high-leverage:

- **Math**: competition problems, theorem statements, proofs. Often from AoPS, MATH dataset, GSM8K-style training sets.
- **Instruction-following data**: query-response pairs in instruction format. This is mostly a post-training concern, but some labs blend a small amount into pre-training.
- **Synthetic data**: generated by previous models. Used heavily in mid-training and post-training; less so in pre-training (because the model needs to learn from ground truth, not from a weaker model).

We discuss synthetic data in detail in Chapter 9 (mid-training) and Chapter 19 (R1 case study).

## 3.3 The pipeline, stage by stage

The pipeline is a series of transformations. Each stage is a substantial engineering project in its own right.

### 3.3.1 Extraction

The first stage is to turn raw HTML / PDF / WARC into plain text. This is more involved than it sounds.

**HTML extraction.** Libraries like `trafilatura`, `jusText`, `resiliparse`, and `readability` extract the main text content from an HTML page, stripping navigation, ads, headers, footers. A frontier lab typically has its own extractor (often forked from one of the above) tuned to preserve structure (headings, lists, code blocks) while removing noise.

Key challenges:
- **JavaScript-rendered content** — the raw HTML may not contain the content; you need a headless browser (Playwright, Puppeteer) to render it. This is expensive at scale; most labs do not do it for pre-training and accept the noise.
- **Tables and lists** — often rendered as complex HTML, hard to extract cleanly.
- **Code blocks** — must be preserved as code, not flattened to text.

**PDF extraction.** For papers, books, and reports. Tools like `pdftotext` (poppler), `pdfplumber`, `grobid` (for academic PDFs), and modern learned extractors (Nougat, Marker) turn PDFs into structured text. The output quality varies wildly: a clean arXiv paper is easy; a scanned book from 1920 is hard.

The DeepSeek-V3 paper mentions that PDF extraction for academic content was done with a custom pipeline. The Qwen3 paper similarly references custom PDF handling. This is not surprising — extraction quality is a competitive differentiator.

**WARC parsing.** Common Crawl comes in WARC format. Parsing a 300 TiB WARC into individual HTML files is a Hadoop/Spark job in its own right.

### 3.3.2 Language identification

After extraction, every document gets a language ID. The standard library is `fastText`'s language identification model, which classifies text into ~200 languages with high accuracy at low cost.

Documents in target languages (e.g., English, Chinese, code) are kept; others are dropped. The fastText model itself is small (~1MB) and runs at millions of documents per second on a single GPU.

A subtle point: language ID errors are a real source of contamination. A document in a minority language might be misclassified as English, polluting the English mix. Frontier labs re-run language ID with stricter thresholds or with multiple classifiers.

### 3.3.3 Quality filtering

This is where the pipeline diverges most between labs, and where most of the iteration happens. Quality filtering has two components: heuristic filtering and learned filtering.

**Heuristic filtering.** A set of hand-written rules:
- Drop documents with fewer than N words or more than M words.
- Drop documents with a mean word length outside [3, 10] characters.
- Drop documents with a symbol-to-word ratio above some threshold (catches code-mixed garbage, encoding errors).
- Drop documents with too many lines ending without punctuation.
- Drop documents that look like navigation menus, error pages, or search result pages (regex against common patterns: "404", "page not found", "JavaScript is disabled", etc.).
- Drop documents that are mostly uppercase.
- Drop documents that contain "lorem ipsum" or other known boilerplate.

These rules are embarrassingly parallel, run on every document, and catch the obvious junk.

**Learned filtering.** A classifier (typically a small model — XGBoost on hand-crafted features, or a 100M–1B parameter transformer) is trained to predict whether a document is "high quality" or "low quality." The training labels come from a small labeled set, often generated by humans or by a strong model (e.g., "rate this document 1-5 for training a language model").

A common approach:
1. Hand-label 50,000 documents on a 1–5 quality scale.
2. Train a classifier (XGBoost or small transformer) to predict the quality score.
3. Use the classifier to score every document in the corpus.
4. Keep only documents above a threshold (often a percentile cutoff).

The classifier is itself trained on outputs from a strong model, which was trained on previous data. This circularity is fine in practice because the strong model has absorbed most of the same quality signal.

The Llama-2 paper introduced a particularly influential approach: train a quality classifier on data labeled by Llama-2 itself, then use it to filter the pre-training corpus. DeepSeek-V3 and Qwen3 use similar approaches.

**A worked example.** A real (simplified) quality classifier:

```python
import xgboost as xgb
import numpy as np

# Hand-crafted features for a document
def extract_features(doc):
    return {
        "mean_word_length": np.mean([len(w) for w in doc.split()]),
        "std_word_length": np.std([len(w) for w in doc.split()]),
        "symbol_to_word_ratio": sum(c in "!@#$%^&*()" for c in doc) / max(1, len(doc.split())),
        "frac_lines_ending_with_punct": sum(1 for line in doc.split("\n") if line.rstrip().endswith((".", "!", "?"))) / max(1, len(doc.split("\n"))),
        "frac_lines_with_capital": sum(1 for line in doc.split("\n") if line and line[0].isupper()) / max(1, len(doc.split("\n"))),
        "mean_sentence_length": np.mean([len(s.split()) for s in doc.split(".")]),
        "log_n_words": np.log(len(doc.split())),
        "frac_unique_words": len(set(doc.split())) / max(1, len(doc.split())),
        # ... dozens more
    }

# Train on 50K hand-labeled docs
X_train = np.array([[f[k] for k in sorted(features)] for f in features_train])
y_train = labels_train  # 1-5 quality

clf = xgb.XGBRegressor(n_estimators=500, max_depth=6)
clf.fit(X_train, y_train)

# Score every doc
scores = clf.predict(X_all)
keep_mask = scores >= np.percentile(scores, 60)  # keep top 40%
```

The threshold (keep top 40%, top 60%, etc.) is itself a hyperparameter that affects model quality. Frontier labs iterate on this threshold.

### 3.3.4 Deduplication

Deduplication is critical. The web has massive duplication: news articles syndicated across sites, scraped content reposted, template pages that differ only in the title. Duplicates in the training data cause the model to overfit to the duplicates and waste compute.

Dedup happens at multiple granularities:

**Document-level dedup.** Hash each document (or its MinHash signature) and remove duplicates. MinHash [\[7\]](../appendix/b-references.md#7-minhash) approximates Jaccard similarity between documents efficiently: a few hundred hash functions can estimate the Jaccard similarity of two documents to within a few percent.

The standard approach:
1. For each document, compute a MinHash signature (a vector of, say, 128 hash values).
2. Use locality-sensitive hashing (LSH) to bucket documents with similar signatures.
3. Within each bucket, compute exact similarity (or Jaccard on the original sets).
4. Keep one document per cluster of near-duplicates.

This is the basis of the `datasketch` library, and most frontier pipelines have a custom version. The DeepSeek-V3 paper references a custom dedup pipeline; the Llama-3 paper uses a similar approach.

The threshold is tunable. Llama-2 used a Jaccard threshold of 0.8; DeepSeek-V3 uses a similar range. Lower threshold = more aggressive dedup = less duplication but more risk of dropping legitimately similar documents (e.g., news reports on the same event).

**Paragraph-level and sentence-level dedup.** Catches cases where a document is mostly unique but has a large chunk copied from elsewhere. Implemented with suffix arrays or suffix trees on the token stream.

**Token-level dedup with suffix arrays.** The most aggressive form: find any sequence of N consecutive tokens that appears multiple times in the corpus, and remove all but one occurrence. This is compute-intensive but catches the worst boilerplate ("subscribe to our newsletter", copyright notices, etc.).

Suffix-array-based dedup is described in the seminal paper by Lee et al. (2022) on deduplicating training data [\[8\]](../appendix/b-references.md#8-deduplicating-training-data), which showed that aggressive token-level dedup dramatically improves model quality and reduces overfitting.

The pipeline in pseudocode:

```python
# Lee et al. 2022 style
# Build a suffix array over the entire tokenized corpus
# For each suffix, count how many times it appears
# Remove any document that has a suffix appearing >threshold times
def aggressive_dedup(documents, threshold=100):
    token_stream = [tok for doc in documents for tok in doc]
    sa = build_suffix_array(token_stream)
    counts = count_occurrences(token_stream, sa)
    
    drop = set()
    for i, doc in enumerate(documents):
        for tok in doc:
            if counts[sa.index_of(tok)] > threshold:
                drop.add(i)
                break
    return [d for i, d in enumerate(documents) if i not in drop]
```

The `build_suffix_array` and `count_occurrences` are non-trivial — the implementation needs to be efficient at terabyte scale, usually with a parallel suffix array builder (e.g., `divsufsort` parallelized with MPI).

### 3.3.5 Contamination removal

Contamination is the silent killer of evals. If your evaluation benchmark is in your training data, the eval score is meaningless.

Standard approach: for every benchmark you care about (MMLU, GSM8K, HumanEval, etc.), compute n-gram overlap between the benchmark and your training corpus. If a training document has an n-gram of length 8 (or 10, or 13) in common with the benchmark, drop the document or the matching n-gram.

```python
def remove_contamination(corpus, benchmarks, n=8):
    # Build a set of all n-grams in benchmarks
    bench_ngrams = set()
    for bench in benchmarks:
        for doc in bench:
            tokens = tokenize(doc)
            for i in range(len(tokens) - n + 1):
                bench_ngrams.add(tuple(tokens[i:i+n]))
    
    # Filter corpus
    clean = []
    for doc in corpus:
        tokens = tokenize(doc)
        contaminated = False
        for i in range(len(tokens) - n + 1):
            if tuple(tokens[i:i+n]) in bench_ngrams:
                contaminated = True
                break
        if not contaminated:
            clean.append(doc)
    return clean
```

The threshold n is a trade-off. n=8 is conservative (catches exact plagiarism). n=13 is stricter (catches reworded plagiarism, but may also drop legitimate documents that happen to share long phrases). Most labs use n=8 to n=13.

A subtler problem: contamination against *rephrasings* of benchmarks. If a benchmark is rephrased and posted on a forum, the n-gram check misses it. Some labs use embedding-based contamination detection (compute embeddings of benchmark items, find nearest neighbors in the corpus, drop if similarity is high) but this is more expensive and less common.

The Llama-3 paper has a particularly thorough section on contamination, including a discussion of how they re-checked for contamination after every major data update.

### 3.3.6 PII and harmful content filtering

Two filters run at the end:

**PII filter.** Regex and named-entity recognition to detect and either drop or mask personally identifiable information: emails, phone numbers, SSNs, addresses, full names in specific contexts. The choice between "drop" and "mask" is a policy decision; some labs prefer to mask rather than drop, to preserve the surrounding text.

**Harmful content filter.** A classifier (often a smaller version of the model being trained) that scores each document for harmful content (violence, sexual content, etc.) and drops those above a threshold. This is in addition to safety training in post-training; the goal is to keep harmful content out of pre-training entirely.

The threshold is itself controversial. Too aggressive and you censor the model; too lenient and the model learns from harmful content. Different labs have different policies.

### 3.3.7 Domain mixing

After all the filtering, the corpus is a mix of domains: web, code, math, books, papers, etc. The final step is to choose the mix ratio.

The mix is tuned to:
- **Match the target use cases.** If the model is for coding, upweight code. If for reasoning, upweight math.
- **Match the evaluation distribution.** If most evals are in English, upweight English.
- **Match the perceived deficits of previous models.** If a previous version was bad at math, upweight math.

The mix is not fixed during the run. Frontier labs monitor validation loss per domain and adjust the mix during the run. The DeepSeek-V3 paper mentions this kind of mid-run adjustment.

A common tool for this is the **DoReMi** approach (Xie et al., 2023) [\[9\]](../appendix/b-references.md#9-doremi), which uses a small proxy model to find the optimal data mix. The mix is then used for the big run.

### 3.3.8 Tokenization

The final step is tokenization. A tokenizer converts text to a sequence of integer token IDs. The choice of tokenizer matters: a bad tokenizer means more tokens per word, which means longer effective sequences, which means slower training and worse compression.

The two main families:

**Byte-Pair Encoding (BPE).** Greedily merges the most frequent pair of adjacent tokens. Used by GPT-2, GPT-3, Llama, most modern models. Vocabulary size typically 32K–256K.

**Unigram.** Starts with a large vocabulary and prunes to a target size. Used by SentencePiece, often for multilingual models. Vocabulary size typically 32K–256K.

DeepSeek-V3 uses a BPE tokenizer with a vocabulary of 128K, optimized for English and Chinese. Qwen3 uses a similar BPE tokenizer. Llama-3 uses a BPE tokenizer with 128K tokens, with special tokens for function calling and code.

The tokenizer is trained on a representative sample of the training corpus. A bad tokenizer choice is a problem that cannot be fixed later — you cannot easily re-tokenize a model. Chapter 4 covers tokenization in detail.

### 3.3.9 Packing and shuffling

The training data loader streams pre-tokenized text, shuffles it, and packs it into fixed-length sequences (e.g., 4096 tokens per sequence, with a smaller effective length if the original documents are shorter). The packing is done with attention masks that prevent cross-document attention (so the model does not learn to attend to the boundary between two documents).

A real data loader in pseudocode:

```python
class PackedDataLoader:
    def __init__(self, token_streams, seq_length, buffer_size=10000):
        self.token_streams = token_streams  # list of numpy arrays of tokens
        self.seq_length = seq_length
        self.buffer = []
        self.rng = np.random.default_rng()
    
    def get_batch(self, batch_size):
        seqs = []
        for _ in range(batch_size):
            while len(self.buffer) < self.seq_length:
                # Sample a random document
                doc = self.token_streams[self.rng.integers(len(self.token_streams))]
                # Add an EOS token
                self.buffer.extend(doc)
                self.buffer.append(self.eos_token)
            seqs.append(self.buffer[:self.seq_length])
            self.buffer = self.buffer[self.seq_length:]
        return np.stack(seqs)
```

The `buffer` carries over excess tokens from the previous batch. The shuffle is over documents, not over individual sequences, which preserves the within-document structure.

## 3.4 The pipeline as a system

The data pipeline is not a single script. It is a distributed system that runs continuously, processing tens of terabytes per day.

A typical implementation:
- **Storage**: S3 or a parallel filesystem (Lustre, WekaFS) for the raw crawl and the cleaned data.
- **Compute**: A Ray or Spark cluster for the processing. Each stage is a separate job.
- **Orchestration**: Airflow, Argo, or a custom workflow system.
- **Monitoring**: dashboards for throughput, error rates, output statistics.

The pipeline must be:
- **Idempotent**: re-running a stage produces the same output. This is critical because failures are common and you must be able to resume.
- **Checkpointed**: each stage writes its output to durable storage, so a failure in stage N+1 does not require re-running stages 1 to N.
- **Versioned**: every version of the corpus is tagged (e.g., `corpus_v3_2024_09_15`), so a training run can be reproduced against a specific data version.
- **Observable**: throughput, output size, output statistics (mean length, language distribution, etc.) are logged and alerted.

A run that takes 60 days at the training stage might take 2–4 weeks at the data preparation stage, and a non-trivial fraction of engineering time is spent iterating on the data mix.

## 3.5 Real numbers from real labs

Concrete numbers, where the labs have published them:

**DeepSeek-V3 [\[1\]](../appendix/b-references.md#1-deepseek-v3):**
- 14.8T training tokens.
- Data mix: heavily English and Chinese, with code, math, and multilingual.
- Custom dedup pipeline, custom quality filtering.
- PDF extraction for academic content.

**Llama-3 [\[5\]](../appendix/b-references.md#5-llama-3):**
- 15.6T training tokens (for the 8B model, which was trained on more than Llama-2's 1.8T).
- Data mix: ~50% English web, ~25% code, ~10% multilingual, ~7.5% academic, ~7.5% "other."
- Heuristic filters (Llama-2-style) + learned quality classifier (Llama-2-based).
- Aggressive dedup with MinHash and suffix arrays.
- Detailed contamination check against 32 benchmarks.

**Qwen3 [\[6\]](../appendix/b-references.md#6-qwen3):**
- ~36T pre-training tokens over three stages, in 119 languages and dialects; no language split is published ([fact sheet](../appendix/fact-sheets/qwen3.md#pre-training-data)).
- Data mix: web, code, STEM, reasoning, books, multilingual and synthetic data, with trillions of tokens of PDF text extracted by Qwen2.5-VL.
- Custom quality classifier.
- Aggressive dedup.

**DeepSeek-R1 [\[10\]](../appendix/b-references.md#10-deepseek-r1):**
- Base model is DeepSeek-V3 (so 14.8T pre-training tokens).
- SFT data: 600K high-quality reasoning examples, plus 200K non-reasoning.
- RL data: 600K reasoning prompts, plus preference data.
- Heavy use of synthetic data: reasoning traces generated by the model itself, filtered for correctness.

The takeaway: the data is the model, and the data is large, multi-stage, and continuously iterated.

## 3.6 Failure modes

The data pipeline fails in interesting ways:

**Distribution shift.** The web changes. Common Crawl snapshots are not i.i.d. — a snapshot from 2024 has different content from a snapshot from 2022. If you train on a mix of old and new, the model learns a mixture of distributions, which can hurt generalization.

**Filter-induced bias.** Heuristic filters can systematically drop certain kinds of text. For example, a filter that drops documents with too many non-ASCII characters will drop most non-English text, biasing the model toward English. Frontier labs are very careful to check that their filters do not introduce bias.

**Quality classifier gaming.** If the quality classifier is trained on a fixed set of features, the training corpus will gradually shift toward documents that score high on those features, even if they are not actually high quality. This is a form of Goodhart's law. Frontier labs re-train the quality classifier periodically and add new features.

**Dedup aggressiveness.** Too aggressive and you drop legitimate content; too lenient and you have duplicates. The threshold is a hyperparameter that the lab tunes during the run.

**Tokenization mismatch.** The tokenizer is trained on a sample of the corpus. If the corpus changes significantly (e.g., a new code language becomes prominent), the tokenizer may not handle it well. The result is more tokens per word, slower training, and worse quality on the new content.

**Pipeline outages.** The pipeline is a distributed system and distributed systems fail. A failure in stage 5 can stall the whole pipeline. Frontier labs have runbooks for every common failure mode, and the on-call rotation for the data pipeline is just as intense as the on-call for the training job.

## 3.7 The JD, decoded

What "Pre-training Data Engineer" means in practice, mapped to this chapter:

| Component of the pipeline | What the engineer does |
|---|---|
| Raw crawl | Negotiate with Common Crawl, run additional crawls, manage storage |
| Extraction | Maintain the HTML / PDF / code extractor, fix extraction bugs, handle new content types |
| Language ID | Tune the language ID classifier, handle multilingual edge cases |
| Quality filtering | Iterate on the heuristic rules and the learned classifier, tune thresholds |
| Dedup | Maintain the MinHash / suffix array dedup pipeline, tune thresholds |
| Contamination | Maintain the n-gram overlap checker, add new benchmarks as they drop |
| PII / harmful content | Maintain the classifiers, tune thresholds, handle policy changes |
| Mixing | Run DoReMi-style optimization, iterate on the mix during the run |
| Tokenization | Train the tokenizer, handle edge cases, manage vocabulary |
| Dataloader | Build the packed-sequence dataloader, tune the shuffling, handle failure recovery |

A pre-training data engineer at a frontier lab is not doing pandas on a CSV. They are maintaining a distributed system that processes tens of terabytes per day, with strict version control, careful contamination checking, and continuous iteration on the data mix.

## 3.8 What you should take from this chapter

1. **Data is the model.** A frontier pre-training corpus is built through a 10-stage pipeline that takes weeks and processes petabytes.
2. **The pipeline is a distributed system.** It runs on a Ray or Spark cluster, with all the operational concerns of a production system.
3. **Quality filtering is a model, not a heuristic.** Frontier labs train classifiers to predict document quality, and the classifiers are themselves trained on outputs from strong models.
4. **Dedup is multi-granularity and aggressive.** Document-level MinHash, paragraph-level dedup, token-level suffix arrays. The Llama-2/3 paper showed that aggressive dedup dramatically improves model quality.
5. **Contamination is a first-class concern.** Every benchmark you care about gets n-gram overlap checked against the corpus.
6. **The mix is iterated during the run.** Frontier labs adjust the data mix based on validation loss curves.
